# Deliberate beta and stable npm releases

## Problem Statement

Anthracite users need a dependable default installation while new behavior receives practical testing. In released 0.6.5, merging a release-please PR creates a release and starts npm publication to the default `latest` channel. We have repeatedly taken that step immediately after implementing a feature. Focused tests passed, but ordinary collaboration and interrupted Git workflows still exposed defects during daily use.

The maintainer needs an explicit separation between trying a candidate and recommending it to everyone. A prerelease version alone is insufficient: channel selection, the source actually exercised, practice results and permission to publish stable must agree. Returning to an older executable also cannot undo completed Git rewrites or make an incompatible pending recovery safe.

The baseline is Anthracite 0.6.5 at merged main `64d82c8a00e7ba97f81ddda2f82f0cca2604606b`. Its working npm bundle, isolated installation checks, release-please integration and OIDC publisher are foundations to preserve. This specification changes release policy and automation; it does not claim to fix every CLI defect or establish Graphite parity.

## Solution

Keep one main development branch and two explicit npm channels: `latest` for a deliberately approved stable release and `beta` for a manually requested candidate. For example, a maintainer can publish `0.7.0-beta.1` without changing `latest`, exercise that exact version, and later approve a separately built and tested `0.7.0` containing the same release inputs.

Keep automatic release-please preparation, but remove automatic npm publication on main pushes and release-PR merges. Extend the existing trusted release workflow with manual beta and stable operations. Both use the existing package build, exact-tarball tests, OIDC and provenance. Neither operation is triggered for every feature commit.

A stable operation selects one immutable beta version and its durable release record, checks practice evidence and verifies source equivalence. Only the narrowly defined release version and generated changelog changes are allowed between the beta source and the stable release source. Different code, dependencies, tests, packaging or workflow inputs require another beta. The stable package receives its own version, build, tests, checksum and publication; moving a dist-tag cannot change the version inside a beta package.

Retain durable candidate identity and evidence, document channel switching and safe recovery, and validate the first actual OIDC beta separately after explicit owner approval. Local implementation tests make no real registry publications or live GitHub changes.

## User Stories

1. As a stable user, I want an ordinary npm installation to select the approved stable release, so that new features do not arrive before practical acceptance.
2. As a beta tester, I want to opt into the beta channel, so that I can try new behavior deliberately.
3. As a maintainer, I want beta publication started manually, so that merging each feature does not create a new public package.
4. As a maintainer, I want beta publication to preserve latest, so that experiments do not change the default installation.
5. As a maintainer, I want canonical beta versions checked before publication, so that a mistaken stable version cannot use the beta route.
6. As a maintainer, I want the stable route to refuse prerelease versions, so that a beta cannot accidentally become the default stable package.
7. As a maintainer, I want source identities resolved to full immutable commits, so that moving branch names cannot change the selected candidate.
8. As a maintainer, I want publication restricted to this repository's verified main history, so that an arbitrary ref cannot become a supported release source.
9. As a beta tester, I want the candidate's source commit and artifact checksum recorded, so that a finding identifies the executable actually tested.
10. As a maintainer, I want beta version staging isolated from my checkout, so that preparing a candidate does not change local branches or stable version tracking.
11. As a maintainer, I want both channels to use the established exact-tarball tests, so that publication preserves the existing distribution guarantees.
12. As a user, I want both an and anthracite available in either channel, so that changing channel does not change command names.
13. As an agent user, I want installed MCP execution exercised, so that the chosen channel works through the existing agent interface.
14. As a maintainer, I want to exercise synthetic stacks before daily use, so that ordinary history and recovery risks are considered before stable release.
15. As a beta tester, I want merged-parent and unpublished-commit scenarios included when relevant, so that successful happy paths are not the only practical evidence.
16. As a beta tester, I want genuine conflicts and interrupted workflows exercised when relevant, so that recovery is tested across processes.
17. As a maintainer, I want practice results tied to one beta version, so that evidence from another candidate cannot authorize release.
18. As a maintainer, I want unresolved findings visible, so that elapsed time alone cannot imply acceptance.
19. As a maintainer, I want a separate explicit stable-publication confirmation, so that preparing a release PR does not recommend the package automatically.
20. As a maintainer, I want stable publication tied to one selected beta, so that a moving beta tag cannot silently change the evidence.
21. As a stable user, I want the released code to match the exercised candidate, so that untested changes cannot enter during promotion.
22. As a maintainer, I want dependency, tool and workflow changes to require a new beta, so that code equivalence does not hide different release inputs.
23. As a maintainer, I want legitimate version and changelog changes allowed, so that a separately versioned stable release remains possible.
24. As a maintainer, I want stable rebuilt and tested with its own version, so that its manifest and reported version are correct.
25. As a maintainer, I want OIDC and provenance retained, so that beta support does not introduce persistent npm write tokens.
26. As a maintainer, I want durable manifests and artifacts, so that a short-lived Actions artifact is not the only evidence for later release or recovery.
27. As a maintainer, I want duplicate and uncertain publication attempts reconciled read-only, so that retries do not publish different bytes under the same version.
28. As a maintainer, I want registry propagation distinguished from publication failure, so that temporary absence does not cause a blind second write.
29. As a maintainer, I want owned publications serialized, so that beta checks and stable writes do not race each other.
30. As a maintainer, I want unexpected tag movement reported without automatic reversal, so that another publisher's work is not overwritten.
31. As a user, I want documented installation by channel and exact version, so that I can reproduce a candidate or return to the approved default.
32. As a terminal user, I want completion verified after channel changes, so that shell suggestions still match the installed command.
33. As an agent user, I want instructions for restarting an existing MCP process after an update, so that an old server is not mistaken for the new executable.
34. As a user, I want downgrade instructions to protect pending recovery, so that changing executables does not corrupt an unfinished operation.
35. As a maintainer, I want a small local validation suite and bounded release jobs, so that release discipline does not require the full CI matrix.
36. As a maintainer, I want one separately approved real beta publication to validate OIDC and tag isolation, so that simulated external responses are not presented as live acceptance.

## Implementation Decisions

1. **One workflow and two manual operations.** Keep the existing trusted release workflow and package identity. Main pushes continue release-please preparation and stable tag/release creation, but cannot invoke npm publication. Manual dispatch selects beta or stable explicitly, with no default publishing channel. Beta requires a full source commit and exact beta version. Stable requires an existing stable release tag, exact beta version, practice-evidence reference and confirmation equal to the intended stable version. Missing or contradictory input refuses before publication. Releasing does not require a second long-lived development branch.

2. **Repository and version constraints.** Dispatch must use the default-branch workflow. Verify the configured repository, exact source commit and membership in main history. Resolve and retain ref identities once, then revalidate effect-sensitive tags rather than silently following moved names. Beta accepts only canonical `major.minor.patch-beta.n`, where n is a positive integer without leading zeroes. Stable accepts only canonical `major.minor.patch`. Reject build metadata, other prerelease names, shell fragments, aliases and unspecified versions. Never reuse a version for a new publication; existing-version reconciliation is read-only. A beta's target stable version and a stable version must be newer than the observed latest stable version. An initial latest value must exist and be a verifiable stable package. Within the same target version, a subsequent beta number must advance past already published beta numbers. A stable operation's version must equal the selected beta's target version. No arbitrary package or registry input is accepted.

3. **Isolated version staging.** Build beta from the selected clean source in disposable staging. Change only the CLI package's version to the validated beta version before the ordinary build; record this transformation. Preserve release-please's stable version tracking, the maintainer checkout, local Git configuration and existing tags. Do not create version commits or run package lifecycle version scripts as a side effect. Stable builds from its exact existing release tag and verifies that the CLI version already matches it. Both commands report the package's own installed version.

4. **Release records.** Introduce one versioned, validated release-record format for this package. It binds channel, package/version, target stable version, repository, source commit, normalized source identity, actual tool versions, staged-version transformation, executing workflow definition and release-process identity, run/attempt identity, artifact checksums, selected dist-tag, latest-before value and verification results. Stable records additionally bind the exact beta record and package integrity, practice-evidence identity and captured content digest, approving actor, intended stable version and source-equivalence result. Malformed, foreign, incomplete or disagreeing records refuse. A supplied evidence reference is data, never executable code or permission to fetch an arbitrary URL. Restrict it to the configured repository's supported GitHub evidence locations and snapshot its approved contents.

5. **Source equivalence.** Compare the full tracked source trees and their entry types/modes using a versioned normalization rule. Normalize only the CLI package version field, that package's release-please manifest version field, and the generated CLI changelog's contents. Preserve all other manifest fields and entries. Do not exclude an entire package manifest, all documentation, all workflow files or arbitrary user-supplied paths. Additions, removals, symlink/type/mode changes, dependency/lockfile changes, test changes, packaging changes and workflow/tool-pin changes outside those precise exceptions require a new beta. Also require the actual executing workflow definition, release-process code and toolchain to match the beta's recorded identities, even when the dispatch commit differs from the checked-out release tag. The declared version transformation, channel and approval metadata differ by operation; those are not new release code. Checking out an older tag cannot conceal a changed dispatcher. Record the normalization rule and digest, and verify equality again before stable publication. The beta and stable tarballs are expected to differ because their versions differ; raw tarball equality between channels is not the source-equivalence test.

6. **Explicit stable gate.** A stable tag or merged release PR only prepares a possible release. Publishing stable requires the manual stable operation, a verified published beta record, acceptable practice evidence and source equivalence. Bind the decision to the exact stable version and beta, rather than inheriting approval from a feature PR, a previous dispatch or a moving beta tag. The authenticated maintainer initiating the confirmed operation is responsible for the practice decision. Every refused gate prevents npm writes. There is no implicit first-release or hotfix bypass.

7. **Practice evidence.** A validated, machine-readable practice record identifies the exact installed beta version, source/artifact record, dates, platform/runtime, scenarios, passed/failed/not-applicable outcomes, findings and maintainer disposition. It can link a readable report. First exercise synthetic stacks; then normally allow two or three working days of personal use. Time alone is not acceptance. For changed Git-rewriting workflows include applicable merged-bottom-PR and local-unpublished-work cases, external trunk advancement during a pending workflow, genuine conflict/continuation and interruption/resumption. Mark genuinely inapplicable cases with reasons. Release-blocking failures, missing required scenarios or a record for another candidate refuse stable publication. An intentionally shorter practice period requires an explicit recorded maintainer justification and still requires scenario evidence. Validate the record and disposition; do not introduce a business-calendar engine or automatic approval timer. Retained public evidence contains synthetic data and summarized outcomes, without credentials or private project contents.

8. **Existing build and distribution contract.** Reuse the existing bundle builder and isolated exact-tarball checks for both channels. Keep locked dependencies, pinned tools, both commands, Node requirements, license/credits/notices, self-launch behavior and installed MCP checks. Record the actual Node, Yarn, Bun and npm versions and require the stable build to use the beta's recorded versions of those tools. Record runner/platform context without promising identical hosted-runner images or bit-for-bit reproducibility across channels. Build, lint, typecheck and test the exact intended version before publication. Publish precisely that successful tarball, with explicit public access, explicit channel and provenance. Check package name/version/contents, checksum and trusted source immediately before the write. A failed build or package check cannot reach publication.

9. **OIDC and permissions.** Retain the existing repository/workflow trusted-publisher relationship and publication-enabled repository setting. Token permission remains confined to the publishing job; use no persistent npm write token and add no approval, administrator or registry-tag-management privilege. Keep publication directly in the configured workflow, avoiding a second caller workflow that changes OIDC identity. Public registry reads establish package/tag state. The separate permission for standalone npm dist-tag mutations is not needed by this design and is not automatically enabled.

10. **Channel invariants.** Beta always publishes with the beta dist-tag; stable always publishes with the latest dist-tag. Do not rely on npm's default. Capture the verified latest mapping before a beta write, then require the same mapping afterwards while confirming the exact beta mapping, package integrity and provenance. Stable verifies that latest resolves to its exact version and that the beta mapping observed before its write is unchanged. Validate installed tarball bytes against the tested artifact. An unexpected mapping or unavailable readback is a failed/unconfirmed completion, not permission to move another tag. Report the known published version, observed mappings and remaining verification. Do not automatically unpublish, deprecate or repair tags.

11. **Serialization and external races.** Serialize this workflow's beta and stable publication operations with the existing shared release concurrency boundary; do not cancel a publication after it has begun. Perform final source, artifact, version-existence and tag checks after acquiring that boundary. This serializes owned operations, not every possible npm account or external workflow. Detect unexpected external movement and stop with its reached state; do not promise an atomic registry compare-and-swap or roll back another publisher. A beta tag change does not alter which immutable beta a stable operation selected.

12. **Durability before publication.** Store the validated intent record, exact tarball, checksum and test summary as durable release evidence before attempting npm publication. Use the candidate's canonical version tag and GitHub prerelease for beta evidence; use the existing stable release for stable evidence. Beta tags bind the captured source commit and are never force-moved. Preserve compact final verification and practice/approval snapshots alongside the release record. Actions artifact expiration must not remove the only copy needed for promotion or recovery. Existing version tags, assets and records cannot be silently replaced; conflicting identities stop the operation. No native executable assets are added. GitHub release preparation alone is not evidence that the corresponding npm channel is available.

13. **Existing versions and uncertain effects.** Inspect registry existence before writing and after any lost/failed publication response. A known existing version is not published again. Read-only reconciliation can confirm completion only when the retained intended record, exact artifact integrity, repository/source provenance and intended tag results agree; a version number alone is insufficient. Never rebuild a different tarball and reuse the same version. Missing evidence, a conflicting version, moved tag or ambiguous readback preserves durable records and requires deliberate inspection. Allow bounded public-registry visibility checks for up to five minutes; expiration reports publication/verification uncertainty without a second publish. A later explicit retry first reconciles fresh state. If publication is verified absent and a write is still authorized, reuse the verified exact retained artifact and append the fresh run/attempt identity before writing; do not overwrite the original intent or confuse a later publisher's provenance with the original attempt. Tests must distinguish failure before a write, a definite registry rejection and a successful write whose response was lost.

14. **Installation and recovery guidance.** Document global installation through the beta and latest channels and by exact version, verification of both command names and their resolved executable/version, existing shell completion setup, and MCP discovery plus restart/reconnection after an executable update. Changing a package must not automatically edit shell configuration, register another MCP server or migrate user metadata. Document returning to a known stable executable, while explaining that it does not revert Git or GitHub effects. Finish an owned pending operation with a compatible executable before downgrading; preserve recovery and inspect blockers instead of deleting state or resetting refs. Package tests use isolated prefixes and configuration only.

15. **First-use acceptance and rollout.** The implementation itself does not automatically publish a beta or stable version. Once reviewed and merged, request separate owner approval for one exact real beta version/source. That acceptance checks the existing OIDC relationship under manual dispatch, public package/version/integrity/provenance, both commands, completion/MCP and unchanged actual latest. Local simulations do not certify this live boundary. Stable publication remains blocked until a beta has completed both publication verification and the recorded practice decision. Existing latest 0.6.5 remains the default until an independently approved stable publication succeeds.

16. **Cost and operator output.** Keep implementation within one PR. Use focused local process/artifact checks; ordinary CI and the full validation matrix remain off for this work. Add no scheduled publication or full-matrix dependency. Preserve bounded release jobs, widening a timeout only if measured focused validation requires it. Summaries name the channel, version, source, selected beta, source-equivalence result, artifact, checks/practice status, actual tag mappings, confirmed writes and precise next action. Return success only after the operation's declared verification completes. Never call a dry-run or a prepared GitHub release a successful npm publication.

## Testing Decisions

Use one primary seam: the executable release process called by the workflow, driven with literal validated inputs and explicit repository context. Exercise its externally observable exit status, diagnostics, produced records/artifacts and publication calls. Use real temporary Git histories, real npm packing and isolated installation; control only the GitHub/registry boundary responses and publication effects. Avoid tests of private helpers, YAML text snapshots or internal step order that does not affect the contract.

The existing bundle builder, isolated offline package-installation checks and installed Git/MCP scenarios provide the prior art. Keep those checks and expose only the minimum process entry needed to share the workflow's actual validation/publication behavior with local tests. Workflow trigger/permission wiring receives local syntax and event-routing checks as a supplement; they cannot replace process/artifact tests or prove live OIDC. New release orchestration runs on its Node runtime. No new native build or broad native CLI regression campaign is needed when no CLI behavior changes.

Retain a compact matrix of cases, input/source/artifact identities, commands, statuses and expected writes. For preservation cases inspect actual Git refs/index/worktree/configuration and the controlled registry state, not only a printed success line. No production credentials are needed by local publication fixtures. Run no real npm publish, live GitHub mutation, owner-installation change, CI run or full matrix as part of those tests. Documentation/issue publication is separate from release acceptance.

After separate approval, perform exactly one real beta publication through the supported default-branch manual workflow and retain its actual before/after tag observations and provenance. A problem at this boundary blocks claiming complete live acceptance; it does not authorize a stable release, token fallback or wider npm permissions.

## Out of Scope

- Implementing new CLI features, completing Graphite parity or revisiting unrelated open defects.
- Automatic beta publication for each commit, scheduled releases or automatic practice approval.
- Additional long-lived release/maintenance branches, parallel beta channels, canary/alpha/RC naming, arbitrary registries or packages.
- Promoting beta bytes by changing their dist-tag and calling them a new stable version.
- An emergency hotfix bypass, automatic downgrades, unpublishing, deprecation or registry-tag repair.
- Persistent npm write tokens, new trusted-publisher identities, standalone dist-tag write permission or administrator/approval privileges.
- Native release assets, the full validation matrix or a new comprehensive CLI test campaign for release-only changes.
- Automatically changing an existing installation, shell configuration or MCP registration, or converting stored stack/recovery formats.
- Claiming practical safety solely from a passing local fixture, a quiet elapsed period or a successful registry write.

## Further Notes

The owner approved this scope and test boundary on 2 November 2026. This is a specification-only delivery. It does not change the current release workflow, npm tags, installed CLI or user projects. Implementation should remain one focused PR; ticket decomposition is a later decision.

The linked [specification basis and source observations](../verification/beta-release-spec-2026-11-02.md) distinguish current 0.6.5 behavior, official platform contracts and new product decisions. They also record the approved test boundary and limitations. In particular, the first real manual OIDC beta and all practical acceptance remain future work, not completed tests.

The npm [dist-tag documentation](https://docs.npmjs.com/adding-dist-tags-to-packages/) supports explicit publication channel selection. The [publish documentation](https://docs.npmjs.com/cli/v11/commands/npm-publish/) establishes version immutability. The existing publisher is retained according to the [trusted-publishing documentation](https://docs.npmjs.com/trusted-publishers/); the first live dispatch validates that wiring rather than assuming it. [GitHub's manual-workflow documentation](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow) describes the dispatch entry point. These sources support platform facts, not the new practice or source-equivalence policy chosen here.
