## Problem Statement

Developers reuse branch names such as `resolve-audit-findings` after a PR has closed or merged. In Anthracite 0.6.11, a historical PR with that name can be displayed as the new branch's PR or treated as an existing submit target. Submit can push the new branch and then fail while attempting to change the historical PR's draft status, leaving the stack partly submitted.

The same identity mistake is more serious in cleanup. Controlled public-package observations show that sync retains an unassociated reused branch, but a retained old PR association can make separately authorized cleanup delete a new branch with unique commits. A branch name and a closed PR state do not establish that the current local work was closed or landed.

## Solution

Give developers predictable PR selection when names are reused. Submission updates a unique current open PR or creates a new one. Inspection can show genuine terminal history without adopting unrelated history or writing metadata. Cleanup requires evidence covering the current local work; an old PR number or cleanup confirmation alone cannot supply that evidence.

Separate three meanings: an open PR eligible for updates, a terminal PR eligible for historical inspection, and proof that local work may be removed. Keep existing stack scope, local work protection, identity checks and recovery contracts. Implement this as one focused PR without a ticket hierarchy or a full CI matrix.

## User Stories

1. As a developer, I want to reuse a branch name after a merge, so that routine branch names need no dates.
2. As a developer, I want to reuse a name after closing an unmerged PR, so that abandoned proposals do not reserve names forever.
3. As a developer, I want submit to create a new PR when only terminal history exists, so that it never edits the old PR.
4. As a developer, I want an actual open PR updated, so that local unpublished commits do not cause duplicate PRs.
5. As a developer, I want an open PR preferred over historical matches, so that normal work remains discoverable after several reuse cycles.
6. As a developer, I want unrelated historical matches excluded before ambiguity checks, so that two old PRs do not block a new branch.
7. As a developer, I want genuine ambiguity to refuse, so that no arbitrary PR receives my changes.
8. As a developer, I want a terminal PR at the branch's exact head to remain inspectable, so that I can understand landed or closed work.
9. As a developer, I want inspection to preserve local metadata, so that looking at a PR cannot attach or detach a branch.
10. As an agent, I want numeric and shell-sensitive branch names treated literally, so that branch discovery cannot address a different PR number.
11. As an agent, I want the same safe selection in noninteractive submit, so that unattended work does not fail on an obsolete draft transition.
12. As a developer, I want draft and publish options applied to the selected current PR, so that historical PR status stays unchanged.
13. As a developer, I want reviewers and assignees applied to the new or current PR only, so that old PR participants are unaffected.
14. As a developer, I want current descriptions and unrelated roles preserved, so that discovery fixes do not regress selective submit.
15. As a developer, I want dependency footers to use the correct PR identities, so that stacks do not point at retired work.
16. As an agent, I want predictable selection errors reported before pushing, so that avoidable lookup failures do not leave half-submitted stacks.
17. As a developer, I want partial external failures reported accurately, so that I can retry without duplicating PRs or losing confirmed progress.
18. As a developer, I want ordinary landed branches cleaned up, so that identity protection does not disable useful sync behavior.
19. As a developer, I want a new branch protected from an old cached association, so that cleanup cannot discard my new commits.
20. As a developer, I want unpublished corrections protected even after a PR closes or merges, so that terminal status does not erase later local work.
21. As a developer, I want cleanup confirmation kept separate from proof of eligibility, so that `--delete-all` is not permission to discard unrelated work.
22. As a developer, I want the fresh-state behavior from #136 retained, so that an actually closed branch remains deletable without unnecessary force.
23. As a developer, I want explicit `delete --force` and its existing safeguards preserved, so that deliberate selected-branch disposal remains available.
24. As a developer, I want empty or locally proven merged work handled offline where already supported, so that safety does not depend exclusively on GitHub availability.
25. As a developer, I want frozen survivors, occupied worktrees and local files protected, so that identity resolution cannot bypass existing protections.
26. As an agent, I want unavailable or contradictory GitHub evidence to refuse safely, so that lookup failure is never interpreted as permission to create or delete.
27. As a developer, I want pending cleanup revalidated when resumed, so that an old plan cannot authorize newly unsafe deletion.
28. As a maintainer, I want focused public CLI regressions and English guidance, so that the rules remain testable without live test PRs or the full matrix.

## Implementation Decisions

- **Operation-specific authority.** The existing PR lookup, submit planning/execution and cleanup planning/revalidation modules must distinguish open update targets, terminal history, proven absence and unavailable evidence. A historical inspection result is not permission to update or delete. No new user-facing command or internal test-only interface is required.
- **Identity first.** Retain configured repository, PR number/URL, literal head name and same-repository owner/name validation. Malformed or contradictory responses, missing required evidence and lookup errors refuse; they are not “no PR.” Preserve compatibility with an absent or empty legacy full repository name when independently supplied owner/name agree; populated contradictions still refuse.
- **Candidate selection.** Prefer a unique valid OPEN PR for the branch. Terminal history must not make that open candidate ambiguous. If no open candidate exists, historical discovery may return a CLOSED or MERGED PR only when its head OID equals the current local branch tip. Filter ineligible history before counting ambiguity; multiple eligible open candidates or multiple exact-head historical candidates still refuse. Use bounded discovery capable of distinguishing zero, one and multiple eligible candidates; truncated or incomplete results must not imply uniqueness. Do not select the first result or assume result order.
- **Equality, not ancestry, for historical discovery.** A previous merged head can be an ancestor of new work, so ancestry alone must not attach a historical PR. An open PR need not equal the local tip: legitimate local-ahead/behind work retains the existing update and reconciliation rules. A stored number is an identity hint that must be freshly validated, not proof that a reused local name is still covered by terminal history. A valid current open candidate takes precedence over a stale terminal association; foreign or unreadable stored identities must not silently relink.
- **Submit creates or updates deliberately.** Resolve selected branches' writable PR targets before the first push. CLOSED and MERGED PRs are never editable targets, even if their heads equal the local tip. If complete validated discovery finds no open target, use the existing create flow and normal new-PR inputs/defaults. Remove the contradictory behavior where terminal state blocks noninteractive creation or interactive “create new” subsequently rediscovers and edits the retired PR. Existing empty-branch and stack-validation refusals still apply; this does not guarantee GitHub accepts a no-diff PR.
- **Revalidate effects and retain scope.** Recheck target state/identity near PR writes. If it becomes terminal before any PR mutation, re-resolve safely within the same approved branch scope; if safe completion is no longer provable, stop with reached-state guidance. After an uncertain create response, reconcile before another create rather than blindly duplicating it. Do not expand submission or push scope, reopen a historical PR, delete its remote branch, or invoke draft transitions on it. Existing remote-write approvals remain authoritative.
- **Roles, bodies and dependencies.** Preserve targeted reviewers/assignees, new-PR draft defaults, explicit publish/draft options, fresh ancestor bodies and idempotent footer repair. Old PR titles, descriptions, roles, draft status and dependency footers must not be mutated by submission of a reused name. Use confirmed current/new PR numbers in the submitted stack. If an unsubmitted ancestor's obsolete identity prevents a valid dependency plan, disclose/refuse without silently submitting it or editing its retired PR. Previews must disclose create-versus-update and the intended role/body/footer effects accurately.
- **Cleanup needs coverage of current work.** Fresh terminal status permits PR-based cleanup only when the verified PR head equals the protected local head being removed. A stored old number, matching name, ancestry of the old PR head or cleanup consent alone is insufficient. Independent existing local empty/merged proof may still authorize removal under its normal guards. A mismatched terminal PR must not refresh/reset the feature from old remote history or turn new/unpublished work into a deletion candidate. Do not invent an OPEN state to represent this uncertainty.
- **Consent and diagnostics.** Sync `--delete-all` and sync `--force` retain their existing distinct powers; neither overrides this new eligibility condition for unlanded feature work. Non-force delete must report that a known closed/merged PR does not cover the current local head, rather than falsely claiming it is open or unreachable. Explicit `delete --force` retains its existing selected-branch discard authority and local safeguards. If fresh PR state and head do cover the branch, retain #136's successful closed/merged deletion and honest cached-state diagnostics. No fabricated cache age is permitted.
- **Keep useful maintenance.** Unassociated new branches remain outside PR-driven cleanup. Protect reused branches with stale associations and genuine branches with post-close unpublished commits. Continue safe independent cleanup and existing closed-descendant cleanup below retained branches. Ordinary separately authorized survivor maintenance may restack retained branches while preserving every unpublished commit; protected work must not be deleted/reset. Keep frozen, worktree, index/worktree and ownership guards.
- **Revalidation and recovery.** Bind planned cleanup to fresh PR identity/state/head and local refs/metadata, then revalidate before deletion or resumption. If current evidence no longer covers the saved work, refuse while preserving reached state and recovery records. Reuse existing operation evidence and compatible optional state where needed; no mandatory migration or deletion of old recovery data. Pinned PR identities in existing review/landing recovery must not be replaced by generic name discovery.
- **Preserving inspection and opt-outs.** `pr` remains read-only, including when showing no current PR or ignoring an obsolete stored association. GitHub integration opt-outs retain their existing command-specific behavior; failures or opt-outs never grant cleanup authority from stale terminal state. Use normal branch/PR metadata update points only for explicitly permitted write workflows. Do not introduce a branch-generation database or assume stored timestamps exist.

## Testing Decisions

- **Approved single seam:** public CLI processes against real temporary Git repositories and bare remotes. Control only external GitHub answers and effects at the existing `gh` boundary. Assert observable refs, files, staging, checkout, metadata, recovery and remote-call outcomes rather than private helper calls or source layout.
- Use the existing submit, PR-inspection, sync/cleanup, frozen-survivor and fresh delete-state fixtures as prior art. Metadata may be seeded to represent legacy/stale states; the operation under test must run through the public CLI.
- Test both CLOSED and MERGED history on different tips, repeated reuse with multiple old PRs, a unique open PR alongside history, exact-head terminal history and true ambiguity. Include a historical head that is an ancestor of new work to reject ancestry-based attachment.
- Exercise both no stored association and a retained old number. Test malformed/foreign/missing evidence, incomplete candidate sets, literal numeric names, and open PRs whose local tips differ due to unpublished work. Inspection must preserve its complete state snapshot.
- Submit must create one new PR instead of editing history, update a real open PR without duplication, preserve legacy PR contents/roles/status, use the new number in footers, and apply role targeting and draft/publish intent correctly. Exercise retry after partial failure and ambiguity/lookup failure before pushing. Existing fresh-ancestor-body and matching-footer controls remain relevant.
- Cleanup must retain the new branch in both unassociated and stale-associated cases, retain local-ahead corrections after closure/merge, and still remove a genuinely landed exact-head branch. Include `--delete-all`, sync force's separate scope and disabled integration. Observe actual branch survival and commit contents, not only a reported plan.
- Retest #136: an OPEN cache with a freshly closed/merged exact-head PR deletes normally; a reopened PR refuses and retains the verified state; unavailable GitHub reports cached uncertainty; local proof and explicit force retain their legitimate behavior. Changed local work not covered by a terminal head must refuse without silently discarding it.
- Include an affected branch with editable descendants, a frozen survivor, occupied worktrees, staged/unstaged/untracked bytes, changed inputs during lookup, and resumed cleanup whose old evidence is now insufficient. Preserve safe independent work and existing ownership/recovery behavior; do not manufacture success by aborting or deleting recovery records.
- Run the focused acceptance selection on Node and native; exercise representative create/update and protected-cleanup cases through an isolated installed npm candidate. Reuse existing shared PR inspection/review/landing controls where resolver changes affect their pinned-identity contracts. Do not claim live GitHub acceptance from controlled answers.
- Add fast relevant regressions to ordinary CI without starting it during specification work. The full matrix stays off. No live test PRs, user-project mutations or active installation changes are part of this spec's acceptance campaign.

## Out of Scope

New commands, branch naming restrictions, automatically dated names, global branch-generation tracking, mandatory metadata migrations, deleting historical PRs or their remote branches, reopening old PRs, fork/cross-host support expansion, changing stack selection or force permissions, redesigning review/landing/get workflows, a new MCP tool, atomic rollback of completed GitHub effects, live GitHub fixtures, CI execution during specification and the full CI matrix.
