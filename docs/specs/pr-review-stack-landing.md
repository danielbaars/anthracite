## Problem Statement

Developers and agents can create, submit and retrieve Anthracite stacks, but reviewing and landing them requires manually coordinating Anthracite, Git and GitHub CLI. A single PR operation does not express how much of a stack should land, which surviving branches must be replayed, or when approvals and checks must be read again after a force-push. Broad synchronization can also clean up unrelated stacks.

The desired workflow is a bounded direct-GitHub capability, not a Graphite service clone. The Anthracite 0.4.0 parity register identifies this as G01. Retained Graphite 1.8.6 help advertises PR opening, an experimental review command and downstack merging, but those help records do not establish their runtime semantics. Anthracite needs its own explicit, testable contract. Its existing raw Git merge passthrough must retain its meaning.

## Solution

Add three stack-aware entry points backed by the user's existing GitHub CLI authentication:

- `an pr [branch]` displays fresh PR information for the selected tracked branch. `--stack` displays the connected stack's PR overview, and `--web` explicitly opens the selected PR on GitHub.
- `an review [branch]` displays the selected PR's diff without changing the checkout. An explicit action submits one approval, changes-requested review or comment review, bound to an explicitly named PR-head commit.
- `an land [branch]` lands the tracked ancestor chain from trunk through the selected branch using direct rebase merges, one PR at a time. It maintains affected surviving branches, preserves PR identity and stops when the next step is unsafe or not ready. `--dry-run` shows merge, maintenance, push and cleanup scope without writes; noninteractive application requires `--yes`.

Keep the merge set separate from the maintenance set. A sibling must not be merged merely because it shares a parent, but it may need a disclosed replay when that parent lands. Recheck GitHub readiness after every such update. Report confirmed, failed, uncertain and unattempted work rather than treating partial completion as success. Existing MCP tools invoke these same commands and confer no publication or approval authority of their own.

## User Stories

1. As a developer, I want to inspect the current tracked branch's PR, so that I do not manually find its GitHub URL.
2. As a developer, I want to name another tracked branch without checking it out, so that inspection does not disturb my work.
3. As a developer, I want an overview of the connected stack, so that I can see which PRs are drafts, reviewed, blocked or merged.
4. As a developer, I want missing PR associations distinguished from authentication and network failures, so that I do not mistake unavailable information for absent work.
5. As a developer, I want fresh PR identity, base and head information, so that stale cached data cannot select the wrong PR.
6. As a developer, I want the PR opened in a browser only when requested, so that terminal and agent inspection remains predictable.
7. As a reviewer, I want the actual PR diff against its GitHub base, so that reviewing a child does not include its entire downstack.
8. As a reviewer, I want the displayed diff associated with an explicit head commit, so that I know what I reviewed.
9. As a reviewer, I want to approve exactly one PR explicitly, so that a review cannot accidentally approve its stack.
10. As a reviewer, I want to request changes with a body, so that the author receives actionable feedback.
11. As a reviewer, I want to submit a comment review with literal body text, so that shell characters and Markdown are preserved.
12. As an agent user, I want the expected head required for a review write, so that my earlier inspection cannot silently approve newer commits.
13. As a reviewer, I want a changed head rejected before submission when detected, so that my review remains attached to its intended revision.
14. As a reviewer, I want a review submitted during a concurrent head change reported truthfully, so that I do not assume the new head was approved.
15. As a reviewer, I want GitHub's own eligibility restrictions retained, so that Anthracite cannot approve on behalf of another user or approve my own PR illicitly.
16. As a developer, I want inspection to preserve dirty files, staging, branch metadata and saved recovery, so that reading PRs does not repair or advance local operations.
17. As a developer, I want landing to select only the trunk-to-target ancestor chain, so that sibling PRs and independent stacks are not merged.
18. As a developer, I want to land only the bottom portion of a stack, so that unfinished higher PRs remain open.
19. As a developer, I want a dry-run that names each PR and its order, so that I can approve the actual merge scope.
20. As a developer, I want the preview to name required surviving-branch replays and pushes separately, so that landing scope does not conceal maintenance scope.
21. As a developer, I want independent stacks and unrelated merged branches untouched, so that landing does not become repository-wide cleanup.
22. As an agent user, I want explicit noninteractive application with `--yes`, so that missing terminal confirmation cannot mean implicit authorization.
23. As a developer, I want terminal cancellation to occur before persistent changes, so that declining a plan needs no cleanup.
24. As a developer, I want drafts and closed-unmerged PRs to stop landing, so that the command does not publish or reopen them implicitly.
25. As a repository owner, I want missing required approvals and failing or pending checks to stop landing, so that the command respects review and validation policy.
26. As a repository owner, I want unknown readiness reported as unknown, so that missing data cannot become permission to merge.
27. As a repository owner, I want a genuine no-checks/no-required-reviews case supported, so that documentation-only PRs are not rejected simply because their check list is empty.
28. As a repository owner, I want no admin override, auto-merge or merge-queue enrollment, so that landing remains an immediate bounded operation.
29. As a developer, I want a merge conditioned on the expected head, so that a remote update cannot be merged as though it were the approved snapshot.
30. As a developer, I want local and remote feature heads reconciled before application, so that unpublished or externally updated work is not overwritten.
31. As a developer, I want trunk advanced only by fast-forward, so that local trunk commits are never discarded.
32. As a developer, I want dirty work, active Git operations, frozen participants and other worktrees checked before merging, so that a predictable maintenance blocker is found before an irreversible remote effect.
33. As a developer, I want merged parents removed through Anthracite-aware maintenance, so that surviving branches retain valid parents and metadata.
34. As a developer, I want surviving PR identities, titles, bodies, roles and draft states preserved, so that landing does not recreate or republish unrelated work.
35. As a developer, I want only the old landed patches dropped during replay, so that each surviving branch retains its own commits and final content.
36. As a developer, I want pushes and branch deletion protected by the remote revisions inspected, so that concurrent remote commits survive.
37. As a developer, I want approvals and checks re-read after restacking, so that stale approval of a previous head cannot authorize the next merge.
38. As a developer, I want a real replay conflict to retain completed work and use existing continuation, so that the workflow does not invent a rollback.
39. As a developer, I want `an continue` to resolve the local replay without unexpectedly merging another PR, so that remote actions remain explicit.
40. As a developer, I want a retry to reconcile already merged PRs and unfinished cleanup, so that successful remote effects are not repeated.
41. As a developer, I want the original target remembered if its branch was removed before interruption, so that I can finish maintenance after the target itself merged.
42. As a developer, I want a rejected or uncertain push/merge reported separately from confirmed progress, so that recovery instructions match actual state.
43. As a developer, I want interruption to stop later work without promising to undo completed merges, so that cancellation has honest limits.
44. As a developer, I want ordinary hooks respected, so that landing cannot silently bypass repository verification.
45. As a developer, I want the original checkout restored when it survives, or trunk selected when it landed, so that the final working location is predictable.
46. As a CLI user, I want quiet and noninteractive execution to avoid prompts, browsers, editors and pagers unless browser opening is explicitly requested, so that automation cannot hang.
47. As a CLI user, I want help, completion and documentation to distinguish review requests from submitted reviews, so that reviewer assignment is not mistaken for approval.
48. As an agent user, I want the existing MCP output and error envelope, so that these workflows require no additional tools or protocol.
49. As a maintainer, I want old stacks and interrupted operations to remain readable, so that this addition does not migrate unrelated metadata.
50. As a maintainer, I want public CLI acceptance using independent Git and external-service observations, so that internal plans do not certify themselves.
51. As a maintainer, I want adapter evidence separated from a bounded live GitHub smoke, so that fixture success is not presented as universal service compatibility.
52. As a repository owner, I want specification publication to start no Actions runs, so that documentation work does not consume the CI budget.

## Implementation Decisions

1. **Vocabulary and compatibility.** A branch has one tracked parent; trunk is the configured single trunk. A merge target is the final branch whose PR should land. The merge set is its unique tracked ancestor chain before trunk, ordered bottom-up. The maintenance set contains surviving tracked descendants whose ancestry or parent must change because a member of that chain landed. Land means both confirmed merging and completion of the disclosed maintenance. Preserve the raw Git meanings of merge, revert and mv, existing submit role behavior and all unrelated command defaults.

2. **Public argument contract.** Each command accepts at most one nonempty literal tracked local branch, defaulting to the physically checked-out tracked branch. Do not reinterpret numeric branch names as PR numbers. Unknown, untracked and trunk targets fail without initialization or tracking. A physically detached HEAD requires an explicit branch for inspection/review; landing requires a checked-out branch and no active recovery. A saved recovery branch override must not substitute for the physical checkout. A pending landing may resolve its original deleted target through its own validated saved identity. No positional PR numbers/URLs, count selector, wildcard target, all-stacks mode or configurable aliases are introduced.

3. **PR inspection.** Default pr output includes configured repository, branch, PR number/URL, title, author, state, draft state, base, full head OID, review decision and available checks/readiness with explicit unknown states. `--stack` adds the connected tracked component beneath the same trunk child, including its fanout; it does not sweep independent children of trunk. Report branches without PRs as such. `--web` opens only the selected PR's validated GitHub URL, even when the stack overview is shown. No browser is launched by default. Inspection does not populate or repair stored PR associations, initialize a repository, fetch into local refs or change continuation/cache contents.

4. **Review interface.** With no action, review displays the selected PR's actual GitHub base-to-head diff and identifies its base and full head OIDs; dirty local files do not become part of that diff. Capture/revalidate identity and OIDs around diff retrieval; a changing response must not be labeled as a stable reviewed snapshot. The mutually exclusive actions are `--approve`, `--request-changes` and `--comment`. Each write requires `--head <full-oid>` matching the fresh selected PR head, in every interaction mode. Accept a single literal `--body` or UTF-8 `--body-file`; reject both together, missing/unreadable files, empty required bodies and body/head options without an action. Request-changes and comment require a non-whitespace body; approval may omit it. No stdin sentinel, editor-based composition, inline review comments, pending-review editing, dismissal or bulk review is added. A supplied action is explicit intent, not permission acquired from a previous preview or an MCP connection.

5. **Review commit identity and confirmation.** Submit the selected review event for the captured commit identity through authenticated gh API execution rather than relying on an implicit latest-head default. Read back the returned review identity, author, event/state, body and commit OID. Re-read the PR head. A server-accepted review for an older head is retained and reported as such with nonzero status; do not claim the new head is approved and do not automatically dismiss or replace that review. Missing/wrong/malformed readback is unverified progress, not success. Never retry an uncertain review POST automatically: users must inspect the reported PR/review before deliberately resubmitting. A completed review is not equivalent to a pending review request or an assignee.

6. **GitHub boundary.** Use the configured repository identity explicitly on every gh request; do not infer the base repository from whichever remote gh happens to prefer. Validate PR repository, number, head repository/ref and base before writes. Use a stored association only as a lookup hint; a stale association with a mismatching head is a refusal, not an excuse to write to that PR or silently relink. Missing gh, authentication/authorization failures, rate limits, malformed output and transport failures remain distinct from no-PR results. Scope this first contract to same-repository PRs on github.com; fork-headed landing, enterprise-host certification and alternate providers are excluded. Do not read or store Graphite credentials, print tokens, or interpolate untrusted names or review bodies into shell commands.

7. **Planning and authorization.** `land --dry-run` computes a fresh plan and reports ordered PR/head/base identities, current readiness/blockers, necessary reparenting/replay, remote head updates, PR base/footer updates and landed-branch cleanup. No local refs, staging, working files, caches, recovery records, PRs or remote refs are written, and no browser/editor/pager is launched. Remote read-only queries are allowed; use isolated temporary reads if Git objects are needed without updating repository state. Exit zero only when a structurally valid plan with currently known readiness can proceed; report blockers and exit nonzero otherwise. In an interactive terminal application prints the same scope and requires confirmation unless `--yes` is supplied. Noninteractive application requires `--yes`; quiet and --no-interactive do not authorize execution. Revalidate after confirmation. --yes accepts the disclosed scope, not changed participants or protection overrides. No force, admin, auto, queue, alternate merge-method or skip-checks option exists.

8. **Scope and early blockers.** Compute the full mandatory maintenance closure, including affected sibling arms below any selected ancestor and descendants above the target. They are maintenance participants, never additional merge targets. Unrelated trunk stacks remain outside both sets. Before the first merge, require a clean index and working tree including ordinary untracked files, a valid initialized repository, no Git operation or incompatible saved continuation, available participant worktrees, editable merge/maintenance participants and usable remote/PR identities. Refuse frozen mandatory participants, divergent or unpublished commits on published participant heads, missing PRs in the merge chain, closed-unmerged/draft merge candidates, invalid bases, unsupported queue policy and disabled rebase merging before remote writes when already known. Each initial merge-candidate base must match its tracked parent; only the next actual merge must already target trunk. Missing PRs and drafts on surviving maintenance branches are allowed: maintain their local ancestry, update an existing matching remote head if present, but do not publish an unpublished branch or create a PR. On resumption, reconcile expected local changes already made by this landing rather than misclassifying them as unrelated unpublished work. Ignore no changes, auto-stash nothing and reset no branch to make a plan pass. Fresh trunk must be fast-forward-compatible with local trunk. Inspect only necessary participants; do not call broad sync cleanup or scope-wide submit that can discover extra targets.

9. **Per-PR readiness.** Immediately before each merge, the next PR must be open, ready, based on trunk and on the expected head. Require a successful GitHub readiness result, no changes-requested decision, all known failing/pending checks resolved and all required reviews/checks satisfied for that head. Neutral or skipped terminal checks are not automatically failures; use GitHub's policy assessment. An empty checks array or empty review decision alone is neither readiness nor a blocker: a documented no-requirements case can proceed, while unavailable/incomplete/unknown policy or mergeability must stop. Do not synthesize an approval when none is required. Do not merge under an administrative/bypass path, change protections, enable auto-merge or enroll a queue. A queue-required repository is unsupported and stops before merge submission. Known later unready PRs are reported by preflight and prevent the initial application; readiness that changes after earlier progress produces a partial stop. There is no indefinite waiting loop.

10. **Direct rebase merge.** Submit one direct rebase merge conditioned on the expected PR-head OID. Prefer the direct GitHub API via gh for this operation so a gh merge convenience path cannot silently enable auto-merge or enroll a required queue. Confirm the PR is actually merged and capture the merged identity/result and remote trunk containing that result; an accepted request, successful exit, queued operation or closed-unmerged PR is insufficient. A correctly associated already-merged ancestor or target can be an explicitly previewed cleanup-only member after its landed identity and unchanged branch tips are verified; never issue a second merge or include unrelated merged branches. Revalidate base/trunk before requests and use available server preconditions, but do not claim GitHub supplies an atomic transaction over the whole stack or a universal compare-and-swap on every policy/base field. A head/policy/base change or uncertain response stops later work and triggers read-only reconciliation before retry.

11. **Scoped maintenance after every merge.** Persist confirmed merge progress before destructive cleanup. Fetch the necessary remote result and fast-forward local trunk; retain and report divergence instead of resetting it. Reparent affected surviving roots to the correct surviving parent/trunk and replay each required descendant in dependency order, dropping only changes already landed. Preserve branch-specific commits, tree content, author/message data within existing replay semantics, frozen state and PR association. Keep all affected descendant refs intact until they have been used as replay inputs. Update only pre-existing relevant remote heads with explicit expected-old-OID leases, including already-merged heads that need no update only as no-ops. For existing surviving PRs update the base and Anthracite-managed dependency footer as necessary, retaining PR number, user-authored title/body, roles and draft status. Do not run role assignment, implicit publish, PR creation or edits to unrelated PRs. Push and PR-base updates are not atomic; report their actual ordering and reached state. Required new CI triggered by ordinary GitHub push/PR events is not suppressed by the feature, but it never dispatches workflows or reruns checks itself.

12. **Cleanup and final checkout.** Delete only confirmed landed local branches and their Anthracite metadata after their mandatory surviving dependents have usable ancestry. Delete only corresponding unchanged same-repository remote branch refs with an explicit lease; an already absent auto-deleted remote ref is harmless after merge identity is verified. A changed remote ref must survive and stop cleanup for inspection, never be force-deleted. Never let gh delete a local tracked branch outside Anthracite's metadata handling. Preserve unrelated branches, recovery files and remote refs. Restore the caller's original branch if it survives; otherwise finish on trunk. If cleanup cannot complete, retain the record and return nonzero even though merging succeeded. Fully complete landing leaves no landed branch tracked, all disclosed survivors updated and a clean working copy.

13. **Revalidation between merges.** Complete the necessary maintenance for a landed parent before attempting the next PR. Re-read that next PR's current head, base, approvals, checks and readiness. Discard earlier readiness observations when its head/base changed; dismissed approvals and pending replacement checks stop with a precise rerun instruction. Do not approve on the user's behalf, wait indefinitely, rerun CI or downgrade the condition to keep the batch moving. Recheck local participants, worktrees, parent relationships and remote leases before their corresponding changes. A newly required participant or broader effect requires a new preview/confirmation; do not silently expand a saved authorized plan.

14. **Bounded recovery record.** Use the existing repository-owned continuation/recovery mechanisms, adding only an optional landing record needed to retain configured repository/trunk identity, original target branch and PR identity, intended merge and maintenance sets, captured revisions and reached phases. Record intent before the first irreversible request so a killed or timed-out process can reconcile an uncertain merge, and retain enough replay boundaries to avoid duplicating landed commits after cleanup interruption. Load and validate this record before generic context repair can erase it or reject its now-deleted target. Do not migrate existing stack/PR data or reinterpret unrelated old continuation. A conflicting or invalid record causes an actionable preserving refusal, never silent clearing. No generic transaction framework, automatic rollback or background worker is introduced.

15. **Retry, conflict and cancellation.** A fresh `an land` for the same recorded target reconciles live PR/ref state with saved progress before repeating any effect, skips confirmed merges and finishes pending maintenance. A different target/repository or incompatible changed scope refuses. After a genuine replay conflict, retain completed merges/reparents and ordinary Git recovery state; report the original project directory and existing an continue path. Continue completes the pending local replay without merging PRs or initiating remote publication, retaining the landing record for explicit land resumption. Raw Git abort cancels only its active rebase, not completed remote merges; require inspection and retain guarded recovery instructions rather than pretending to resume a nonexistent replay. Hook failures, rejected pushes, authentication expiry and uncertain writes report their actual phase; automatic transport retry must not repeat a write. Cancellation/MCP timeout can leave completed or in-flight remote effects; stop starting subsequent steps and require read-only reconciliation on the next application. Clear only owned completed recovery state after all disclosed work is confirmed.

16. **Output and execution policy.** Use existing CLI error conventions: zero for confirmed inspection/review success or fully completed landing, nonzero for invalid input, blockers, unverified effects or incomplete maintenance. Essential scope, confirmed merges, pending/failed/uncertain actions and recovery guidance remain visible in quiet mode. An explicit web option is the only browser request; effective noninteraction disables incidental prompts, editors and pagers. Honor existing verification/hook policy and owner-checked locking; --yes does not bypass hooks. A failing maintenance hook stops at that phase, retaining earlier remote effects. Read-only pr, review-without-action and dry-run use the preserving inspection path rather than generic mutation initialization/cleanup. Review writes change GitHub only; they preserve local work and recovery data. Existing MCP learn_an/run_an_cmd describe and execute the same literal arguments and ordinary result envelope. No new MCP tools, authentication scheme or independent approval mechanism.

17. **Implementation boundaries.** Extend the existing explicit command registration, scoped GitHub adapter, engine participant/replay/cleanup operations, continuation handling, help, completion and MCP learning. Prefer reuse behind these public interfaces over a parallel stack engine or shell script orchestrator. Reuse selection primitives without assuming all commands' default scopes match. The current test-scope defect B01 is independent: never rely on an test scope flags to bound this feature's validation. Preserve existing metadata names, unrelated saved operations, raw Git passthrough and submit/get/sync behavior.

## Testing Decisions

The approved primary seam is the public CLI process, using real temporary Git repositories and local bare remotes with only the external gh boundary controlled. Good tests assert independent branch/ref/tree/commit observations, PR/review state and actual external effects, not private planner shapes or implementation helper calls. The external adapter must apply real rebase-merge effects to the bare trunk and model new merge OIDs; merely marking a PR MERGED cannot validate replay or cleanup.

Use the existing submit CLI fixture, isolated gh replacement, role-progress failure cases, protected structural replay/continuation scenarios, inspection recovery-preservation cases and real stdio MCP client as prior art. Extend that small boundary to cover the required reads/writes; do not mock the Anthracite engine, Git or its restack implementation. The fixture must fail on unsupported calls instead of making unknown behavior succeed. Changing service state between requests must be deterministic. Public process status/output and independent state are acceptance evidence; an invocation log alone is only supporting evidence.

| T2 — read-only local state | Dirty staging/unstaged/untracked work, explicit inspection during recovery and detached implicit refusal preserve physical HEAD, index bytes, working files and saved continuation. No-action review and land preview do not initialize, fetch into local refs, delete stale recovery or write a cache. |

Run focused acceptance and affected regression groups locally on Node and an independently compiled native executable. Use one installed npm/MCP smoke when validating the implementation artifact; do not duplicate the whole acceptance matrix through MCP or add a new test framework. Record per-runtime results and service boundaries, not a sum advertised as universal parity.

A later bounded live GitHub smoke must be designed and explicitly authorized before remote writes, using a disposable fixture with CI disabled by fixture setup. Exercise a two-PR chain plus an affected surviving arm: inspect/diff, submit a comment review, land a prefix, verify real rebase results/PR base maintenance and finish cleanup. Approval/request-changes requires a distinct eligible reviewer identity if available; otherwise retain a clear adapter-only limit rather than asking the author to self-approve. Respect actual repository requirements and any pending checks. Do not create accounts, change protections or bypass policy to obtain a passing smoke. Live evidence does not certify all organizations, rulesets, checks or platforms. None of these service-changing tests is authorized by publishing this specification.

Specification validation is limited to document structure, coherent public contracts, source/primary-documentation references, link checks and clean documentation-only diffs. Do not run CI or the full matrix to publish this specification. Later implementation may use the existing cheap automatic CI only when authorized; full validation remains manual and excluded from this delivery.

## Out of Scope

- Graphite accounts, API emulation, hosted review/AI features, stack web pages, merge queues and service-side automation.
- Replacing raw an merge or expanding raw Git passthrough meanings.
- Squash/merge-commit landing methods, auto-merge, admin overrides, bypass flags, automatic approvals, protection/ruleset edits, workflow dispatch or CI reruns.
- Cross-repository/fork landing, enterprise certification, multiple trunks, alternate remotes/providers, arbitrary PR-number/URL targets, count selectors and all-stack batch landing.
- Inline/diff-position review comments, editing/dismissing pending or submitted reviews, batch reviews, reviewer assignment changes and a general PR editor.
- Automatic submission of missing PRs, implicit publication of drafts, broad sync cleanup, unrelated branch deletion, forced resets, automatic stashing or unfreezing.
- General undo/abort/rollback, reversal of completed merges, a generic transaction engine, background retries or a claim of exactly-once effects across GitHub and Git.
- Fixing B01 test scope, resuming deferred log issue #12, new MCP tools, exhaustive platform/shell matrices, release publication or changes to the user's installation.
