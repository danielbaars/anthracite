# Opt-in restacking during submission

## Problem Statement

Developers and agents cannot submit a stale local stack in one Anthracite operation. Anthracite 0.6.0 refuses a feature branch that is no longer based on its selected parent and requires a separate restack command. That workaround works, but the caller must coordinate repair scope, publication scope, conflict recovery and a second preview. A broad restack can also reach branches the caller did not intend to submit.

The bounded comparison with Graphite 1.8.6 demonstrates an explicit submit restack option and selected-chain/fanout repair. It also demonstrates behavior Anthracite should not copy: Graphite rewrites local history during a restack-enabled dry-run and can report a successful preview while skipping an occupied stale branch. Existing-PR metadata editing concerns and additional review modes are separate work.

The implementation baseline is released npm Anthracite 0.6.0, main commit `eb23e4f8e924da24e00ae06484799687adde66b1`. This document specifies a new workflow; it does not claim that the feature already ships or that the comparison certified live publication after repair.

## Solution

Add opt-in `--restack` to submission. Determine the chosen publication candidates and required local repair before rewriting anything. Repair the eligible selected histories in parent-first order, validate the reached state, then use the existing submission workflow. Keep ordinary submit behavior when the option is absent or explicitly false.

Keep local repair separate from publication authority. Do not run sync, pull or reset trunk, clean up branches, add unselected stack arms, publish excluded work or broaden role targeting. Existing metadata approvals, draft choices and push protection remain applicable.

A restack-enabled dry-run shows the repair and publication plans without executing replay, staging files or publishing. It can explain that replay may conflict; it does not need to simulate every rebase to promise success. A genuine application conflict stops before any publication and retains a bounded local continuation. Continuing finishes local repair only; publication requires a fresh explicit submit invocation.

For a changed base with a selected child and tip, repair that chain. Leave an unselected sibling on its existing head and report any remaining stale work. An explicitly selected fanout includes its chosen arms, while an independent trunk stack remains outside the operation.

## User Stories

1. As a developer, I want opt-in repair during submit, so that I can prepare and publish my chosen stack in one operation.
2. As an existing user, I want ordinary submit defaults preserved, so that upgrading does not silently authorize local rewrites.
3. As an agent user, I want explicit true, false and negative option forms, so that automation can state its intent unambiguously.
4. As a developer, I want existing submit aliases supported, so that familiar command routes retain the same contract.
5. As a developer, I want the starting branch and stack scope respected, so that repair follows the intended publication task.
6. As a terminal user, I want interactive selection completed before repair, so that unchosen branches are not rewritten first.
7. As a developer, I want update-only eligibility resolved before repair, so that missing PRs do not become implicit publication targets.
8. As a developer, I want unchanged eligible PR branches reconsidered after replay, so that rewritten commits are actually submitted.
9. As a developer, I want an excluded parent used only as a verified unchanged remote anchor, so that submission cannot depend on unpublished parent changes.
10. As a developer, I want selected branches repaired parent-first, so that every branch uses its actual parent rather than a preceding sibling.
11. As a developer, I want unselected descendants and sibling arms preserved, so that a narrow submit does not rewrite unrelated work.
12. As a developer, I want independent trunk stacks excluded, so that one submit cannot repair the entire repository unexpectedly.
13. As a developer, I want pending stale work named, so that success does not imply every tracked branch was repaired.
14. As a developer, I want aligned histories left intact, so that the option does not rewrite commits unnecessarily.
15. As a contributor, I want authors, complete commit messages and unique changes preserved through replay, so that local maintenance retains ownership and content.
16. As a developer, I want a preview of local repair separately from remote effects, so that I understand both scopes before applying.
17. As a developer, I want dry-run to preserve branch history and local work, so that inspection cannot perform the rewrite it describes.
18. As a developer, I want known blockers reported during preview, so that an unsafe plan does not appear ready.
19. As a developer, I want preview uncertainty stated honestly, so that a plan is not mistaken for proof of conflict-free execution.
20. As a terminal user, I want cancellation and confirmation before repair, so that declining publication does not unexpectedly leave rewritten branches.
21. As a developer, I want frozen branches to remain protected anchors, so that repair cannot rewrite or push someone else's protected work.
22. As a developer, I want occupied changing branches refused early, so that another worktree remains intact.
23. As a developer, I want unrelated protected arms excluded from preflight, so that they do not prevent a valid narrow operation.
24. As a developer, I want staging, unstaged work and path collisions protected, so that repair cannot discard local files.
25. As a developer, I want unexpected participant changes refused, so that an earlier plan cannot authorize a different rewrite.
26. As a developer, I want incidental Git update-ref behavior contained, so that my unselected branch refs stay unchanged.
27. As a developer, I want every planned local repair completed before the first push, so that a late replay conflict cannot leave a partly published stack.
28. As a developer, I want a real conflict retained with useful diagnostics, so that I can resolve it using normal Git files.
29. As a developer, I want fresh-process continuation limited to its saved local work, so that restarting cannot expand the branch selection.
30. As a developer, I want continue-all protection checked before staging, so that a newly blocked operation does not stage my files incidentally.
31. As a developer, I want continuation to avoid all publication, so that resolving a conflict never silently submits a PR.
32. As a developer, I want a new explicit submit after recovery, so that changed heads and service state receive fresh validation.
33. As a developer, I want raw abort and ambiguous failures explained, so that I do not mistake active-rebase cancellation for complete rollback.
34. As a developer, I want the original checkout restored after local repair, so that submitting another branch does not navigate me away.
35. As a developer, I want failed checkout restoration reported, so that successful publication is not claimed from an unexpected local state.
36. As a developer, I want push leases retained across repair, so that concurrent remote work cannot be silently overwritten.
37. As a developer, I want explicit force kept separate from local protection, so that it cannot bypass frozen or worktree guards.
38. As a developer, I want draft and ready transitions preserved, so that restacking does not change a PR's publication state by itself.
39. As a developer, I want reviewers and assignees kept on their chosen PRs, so that repairing a stack does not broaden role changes.
40. As a developer, I want existing PR identities and managed-footer behavior retained, so that repair does not replace PRs or user metadata unnecessarily.
41. As a developer, I want partial remote failures to identify reached work, so that I can retry deliberately without assuming rollback.
42. As an agent user, I want noninteractive and quiet execution without surprise prompts, so that the workflow remains usable through MCP.
43. As a maintainer, I want public-CLI tests using real Git and controlled service responses, so that tests verify effects rather than internal plans.
44. As a maintainer, I want one bounded MCP smoke and targeted package/runtime checks, so that delivery is verified without a full validation matrix.
45. As a repository owner, I want specification publication without CI or live fixture mutations, so that this design step starts no runner costs or PR experiments.

## Implementation Decisions

1. **Interface and compatibility.** Add a boolean restack option, default false, to all existing submit routes, including `s` and `ss`. Support explicit true/false and normal negative forms. Preserve each route's existing stack default and other option meanings; add no short alias, persistent setting or automatic prompt that changes the ordinary default. Calls without enabled restack retain their existing behavior.

2. **Selection before effects.** Resolve the starting tracked branch, ancestor/descendant scope, frozen exclusions, effective interactive selection and update-only eligibility before any replay. Use the existing interaction rules: dry-run/noninteractive invocation does not secretly activate an ignored selection prompt. Publication candidates are eligible chosen branches, including initially unchanged existing PR branches whose status may change after replay. Update-only excludes branches without an eligible existing PR, including when always is supplied; excluded branches receive no replay, push, PR creation or role additions. An explicit excluded roles target is an error before replay. An empty effective selection reports a no-op without repair or publication.

3. **Anchors and bounded repair.** Derive required replay only within the effective chosen editable candidates, processing each actual parent before its children. A parent excluded by selection, update-only or frozen policy must satisfy the existing remote-base consistency requirement; when a selected child's publication would rely on unpublished parent changes, refuse rather than adding or rewriting that parent. Unselected children, siblings, independent stacks, trunk refs, parent relations and freeze state remain outside the rewrite. Report relevant stale work left outside the selection. Preserve other refs even with Git's update-ref configuration enabled; never reset an unrelated concurrently changed ref back to an earlier snapshot.

4. **Planning and validation.** Reuse the submit planner/validation and scoped restack engine through their existing boundaries, rather than invoking a repository-wide public restack or sync command. Capture the relevant selected heads, parents, anchors, checkout and remote expectations. Identify known dirty-state, collision, protection, PR-identity, empty/closed-PR and remote-base blockers before replay; retain existing explicit choices where applicable. Collect known required choices before local effects. A branch becoming empty because replay drops an already-applied patch is checked again before publication; do not invent cleanup or a new empty-PR policy.

5. **Preview contract.** Enabled-restack dry-run does not fail merely because selected feature ancestry needs repair. It names planned repairs, anchors/skips and prospective create/update/no-op, draft, role and existing managed-footer effects. A repaired initially unchanged branch must not be incorrectly promised as a final no-op. Preserve branch heads and trees, logical index/staging and working-file content, physical checkout, topology/frozen status and existing recovery data. Create no replay/recovery queue, launch no rebase, stage nothing and perform no push or GitHub mutation. Read-only service discovery and existing administrative/verified PR-cache refresh remain permitted; this is not a byte-for-byte filesystem transaction. Known application blockers return nonzero. An otherwise valid stale plan can return success while explicitly stating that replay and its final heads/conflicts remain unexecuted and unproven; a speculative rebase simulator is not required.

6. **Confirmation and interaction.** When effective terminal confirmation is requested, show the repair/publication plan and obtain confirmation before replay. Cancellation or rejecting selection/confirmation leaves local history and remote state intact, apart from permitted administrative discovery. Preserve existing noninteractive/quiet rules, including ignoring confirm where it is already ignored; enabled restack is explicit local-repair intent, not a bypass of external publication approvals. Metadata/reviewer prompts retain their current meanings and do not authorize extra branches.

7. **Guarded local execution.** Validate planned changing participants before the first replay, then check relevant heads, parents, protection, occupancy and files again before subsequent effects and around hooks. Protect staged/unstaged tracked work and untracked/ignored collisions without automatic stash or discard. Physically unaffected/unselected occupied or frozen arms must not cause broad refusal. Baseline frozen anchors are skipped under existing policy; a newly frozen required editable participant blocks advancement rather than silently changing the saved plan. Keep hooks enabled by default and existing explicit verification controls; neither force nor skipping hooks grants a worktree/frozen exception. Reuse ordinary replay semantics for author/message/content preservation and Git's legitimate already-applied patch elimination; avoid gratuitous rewrites of aligned branches.

8. **Repair/publication barrier and checkout.** Complete all selected local repair, verify the expected reached graph and restore the original attached branch identity before the first push or PR mutation. An original selected branch is restored at its authorized new head, not reset to its old commit. Invocation from an unrelated attached branch with an explicit starting branch restores that unrelated checkout. This feature adds no detached-HEAD application support; refuse that new rewrite path before effects rather than inventing a checkout target. A missing original branch, occupancy/collision, checkout-hook failure or unexpected final state returns nonzero with reached work and no publication. Do not recreate or reset a ref to fake restoration. Verify actual final checkout and effects again before reporting full success.

9. **Fresh post-repair submission.** Recompute outgoing action/status from reached heads within the same resolved selection; do not reuse pre-replay head values or skip a newly changed branch because it was previously up to date. Revalidate PR/repository/head/base identities and relevant blockers before publishing. Discovery changes cannot silently substitute another PR, create a replacement or expand selection. Normal absence and explicit existing submit choices retain their meanings; a race after confirmed planning stops with reached local work. Preserve ordinary draft/publish, role targeting, assignee resolution, additive review requests, existing PR identities and metadata behavior. This round does not repair the separate existing-PR title/body concern.

10. **Remote effects and failures.** After the local barrier, use the existing parent-first submit workflow, force-with-lease default and explicit force policy. Repair must not silently renew a lease expectation to accept intervening remote work; a competing remote head is a failure under the ordinary protected push contract. Force retains only its explicit remote overwrite authority. Preserve existing managed dependency-footer maintenance, including applicable existing ancestor PRs; disclose these ancillary edits separately from pushed heads and do not introduce sibling publication. Stop at the first remote failure, naming repaired local heads, confirmed pushes/PR/role effects and work not attempted. Preserve those effects; provide no transaction, exactly-once or automatic rollback promise.

11. **Local conflict continuation only.** A genuine selected replay conflict returns nonzero before any push, PR write, role addition or footer edit. Retain the actual conflict and a bounded owned local replay queue, original checkout intent and the participant identities needed for safe fresh-process continuation in the original worktree. Reuse existing continuation machinery where sufficient; any additional context is optional, backward-compatible local state, not a deferred publication job. Persist no executable future PR/role/force action. Completing this local continuation requires no GitHub login or service readback. Continue and continue-all revalidate ownership and every pending changing participant before staging or replay. They resume only the saved local repair and final checkout, never fetch new feature heads, add branches, push or call GitHub write helpers. On completion instruct the caller to run a fresh explicit submit with its intended options; existing user approvals remain authoritative when still applicable.

12. **Recovery limits and existing workflows.** Preserve foreign/pending recovery before starting another rewrite. A missing, altered, foreign or stale saved intent, raw-aborted rebase, non-conflict interruption or uncertain metadata/ref publication requires preserving refusal and deliberate inspection rather than consuming state, deleting recovery or rerunning patches blindly. Raw rebase abort cancels only that active rebase, not earlier completed rewrites. Finish a pending new submit repair before downgrading if optional recovery context was added. Preserve ordinary restack, get/sync, structural and landing continuation contracts, including landing's local-only continue boundary. Do not redesign general crash recovery or introduce automatic publication resumption.

13. **Delivery surface.** Update submit help, completion, user guidance and existing MCP learning with opt-in/default, scope, preview and local-only recovery behavior. Use the existing MCP execution tools without another server, tool or protocol. Keep the feature standalone with direct GitHub authentication, and retain repository-required English documentation. The specification and its supporting documentation are published on a documentation branch and as one ready-for-agent issue; no implementation, implementation PR, live fixture or CI execution is part of this delivery.

## Testing Decisions

1. **One primary behavioral seam.** Exercise built public CLI processes with real temporary Git repositories, isolated configuration, local bare remotes and controlled external GitHub responses. Reuse existing submit, frozen-submit, preview, scoped-restack, continuation and interaction fixtures. Independently inspect local/remote refs and trees, commit authors/messages/own changes, topology/protection, logical staging, working files, checkout, recovery and recorded external effects. Do not mock the engine/rebase or assert private planner objects, array order or internal callback counts as correctness.

2. **Selection and compatibility.** Cover a clean chain, stale selected ancestors, fanout, an unrelated trunk stack, an explicit starting branch from another checkout, chosen/unselected descendants, true/false/negative restack forms and submit aliases. Include narrow interactive selection, update-only exclusions, an unchanged eligible PR becoming changed after replay, empty effective selection and an invalid roles target. Include a valid remote anchor and refusal when an excluded parent has unpublished changes. Prove unselected refs remain unchanged with update-ref configuration enabled. Keep bounded controls for ordinary no-restack submit behavior rather than retesting every existing command combination.

3. **Preview, confirmation and known blockers.** On a stale chain, dry-run with enabled restack reports separate repair and remote plans without performing either. Inspect before/after logical local work, heads, topology, recovery, bare heads and service-write logs. Show that predicted outgoing work accounts for repair and skipped/update-only/frozen branches correctly. Check known worktree/dirty/identity blockers, declined confirmation and selection cancellation before replay. Use existing real terminal helpers where actual prompting matters. Do not test guessed wording or require dry-run to discover every future replay conflict.

4. **Successful repair and publication ordering.** Apply clean-chain and selected-fanout workflows with actual Git replay and actual pushes to bare remotes. Verify preserved own changes, authors and complete messages; aligned and excluded branches remain intact. Use independent Git/hook witnesses and the controlled service log to prove the entire selected local repair and original checkout restoration precede the first remote effect. Check newly changed heads are pushed and PRs retain correct existing identity/base, draft state, targeted roles and managed footer behavior.

5. **Protection and races.** Test a frozen anchor, an occupied changing branch, a protected unselected arm, tracked dirt and a representative untracked/ignored collision. Include a late queued-participant protection/identity change and a competing remote update before protected push. Refusals preserve reached work and do not silently widen scope or refresh overwrite permission. Check selected worktree content as well as refs. These are targeted guard cases, not a new exhaustive hook/interruption matrix.

6. **Conflict and fresh continuation.** Construct a genuine replay conflict after some earlier local repair. Assert nonzero, retained reached work and zero push/PR/role/footer effects. Resolve deliberately and continue in a new CLI process; verify only the saved local scope completes and original checkout returns, with remote state still unchanged. Check protection before continue-all staging and preserving refusal for wrong/foreign or raw-aborted recovery. Finally run a fresh submit to publish the repaired intended selection. Cover an existing unrelated continuation route as a bounded compatibility control.

7. **Post-repair refusal and partial publication.** Exercise a checkout/hook failure before the local barrier and a selected branch becoming empty or invalid after replay. These stop before publication and report local repair. Separately reject a push or controlled PR operation after earlier confirmed remote work; verify truthful confirmed/unattempted progress, retained commits and roles, no rollback claim and no implicit continuation publication. Retain lease, draft/publish and per-PR role behavior with focused existing regressions, without sweeping metadata editing into this feature.

8. **Runtime and installation delivery.** Run the focused new and directly affected regressions on Node and native builds. Add exactly one bounded smoke through the existing MCP execution route, preferably using the isolated installed npm bundle so option forwarding, local repair and controlled publication share the same scenario. Reuse the existing curated package checks for both commands/help and add only the needed installed feature coverage. Perform appropriate local build/typecheck/lint and documentation checks during implementation. Do not use the known ineffective test scope selectors to bound execution.

9. **Evidence qualification.** Keep the historical seven paired submit cases and five component controls at their original version/evidence boundary. This spec's scenario list is planned acceptance, not passing tests or additional Graphite observations. No live GitHub mutations, CI, full suite/full matrix or cross-platform certification is needed for this approved test boundary. Future live publication validation needs a separately scoped fixture and authorization.

## Out of Scope

- Making restack the ordinary submit default or adding a persistent preference.
- Repository-wide sync, incoming feature refresh, trunk pulls/resets, cleanup, new tracking, remote-only discovery or multi-trunk support.
- Rewriting or publishing additional siblings/descendants to make an otherwise narrow plan succeed.
- Repairing existing-PR metadata propagation, adding granular edit fields, re-request-all, team-review shortcuts or other submit modes.
- Graphite backend emulation, hosted AI/web submission, auto-merge, merge queue and new authentication flows.
- General undo/abort, arbitrary crash rollback, exactly-once service effects or automatic remote resumption after continue.
- A speculative full-replay preview engine, byte-for-byte cache/index administration immutability, exhaustive platform coverage or a new internal testing interface.
- Implementation tickets, implementation code/PR, npm publication, installation changes, live GitHub fixture mutation, CI and the full validation matrix during specification delivery.
