## Problem Statement

Developers and agents address review feedback while working above the commits that introduced the affected lines. Anthracite can amend a current commit and restack branches, but cannot distribute staged changes automatically among earlier commits. Manually checking out each destination, separating hunks, amending and replaying branches is slow and risks committing unrelated local work.

The pinned practical comparison confirms that installed npm Anthracite 0.2.1 rejects absorb. Graphite 1.8.6 can assign changes to different earlier commits, including multiple commits in one branch and separate hunks in one file. Its measured limits also matter: dry-run can write the index, newly staged files can disappear from its leftover report, and an invocation from a middle branch can leave an upstack branch stale. The requested feature must provide useful local parity without copying those weaknesses.

## Solution

Add absorb and its ab alias to the existing CLI. Inspect staged ordinary text hunks, identify eligible commits in the current tracked branch and its downstack before trunk, show the proposed destinations and leftovers, amend the selected commits, and replay every mandatory tracked descendant. Retain branch names, parent relationships, original authors and complete commit messages, local PR identity and the caller's checkout. Absorbed changes become committed; unabsorbed staged input and formerly unstaged work keep their respective roles.

Support --dry-run/-d, --force/-f, tracked-only --all/-a and interactive --patch/-p through existing global interaction and cwd rules. Dry-run must not change user Git/stack/recovery state. Predictable protection or worktree blockers must fail before staging or rewriting. A genuine replay conflict preserves reached work and supports fresh-process continue; failures without an active rebase get an honest, executable recovery path instead of a rollback claim. Agents use the existing MCP execution tool; no new tool or Graphite service is needed.

## Implementation Decisions

1. **Public interface and flag combinations.** Register absorb with default alias ab. The four boolean options are --dry-run/-d, --force/-f, --all/-a and --patch/-p. There are no positional operands, target-branch selectors, custom messages, custom jobs or new MCP tools. Reject unknown operands/options normally. --all and --patch are mutually exclusive when active; --dry-run with --patch is refused before prompting because dry-run must not stage. Explicit false values do not activate an incompatible option. --force with dry-run is permitted but has no application effect. Existing global cwd, quiet, interaction, verification and error handling remain authoritative except for the explicit absorb rules below.

2. **Source and history boundary.** Use the physically checked-out tracked feature branch selected by the effective cwd, never a saved continuation branch override. Refuse trunk, detached HEAD, an untracked/uninitialized source, unresolved index entries, incompatible index state, invalid tracking and active Git merge/rebase/cherry-pick/revert or saved Anthracite recovery before cleanup, auto-tracking or initialization. The candidate corridor is the unique tracked downstack from the current branch through its ancestors, excluding trunk, with current branch commits included. Each corridor own-commit range must be linear and synchronized with its recorded current parent; refuse stale corridor bases with instructions to restack deliberately. An empty current branch may anchor eligible ancestor commits. Off-corridor tracked descendants may be stale if the existing recorded replay base is valid. Merge-containing mandatory rewrite ranges are outside this first version and refuse before effects.

3. **Immutable inputs and hunk selection.** Plan from saved source/parent tips, own-commit ranges, tracking/protection data and the prospective index tree. Treat ordinary text edits as independent contiguous changed-line hunks with line-position/context translation through history; unrelated hunks in one file must not be collapsed to a single file owner. Search newest to oldest, using exact, deterministic patch commutation: passing a commit requires an equivalent placement before it which produces the same content in both application orders. Choose the most recent eligible commit at which that hunk cannot commute further, provided the amendment itself is representable exactly. The same area having several historical changes therefore chooses its most recent noncommuting eligible owner, rather than arbitrarily selecting among authors or branch names. Reaching trunk, ambiguous repeated context, failed exact translation or an unsupported entry leaves the hunk unassigned. Do not use semantic/AI ownership, filename-only routing or fuzzy application to guess a destination. Multiple hunks selected for a commit must form a compatible exact amendment; any invalid combined application is a planning refusal, not silently duplicated or dropped content. This defines external behavior without mandating a private library or algorithm implementation.

4. **Frozen candidates and bounded text support.** Frozen branch commits are not amendment destinations. Treat an unchanged frozen branch as a boundary/anchor: a hunk owned only below that protected boundary remains input, rather than being redirected into an editable child. Editable commits above it may receive their own hunks. Ordinary modifications, line insertions and line deletions within existing regular text entries are supported, including separate hunks and multiple commits per branch. New entries, whole-entry deletions, binary modifications, renames/copies inferred as entry changes, mode/type changes, symlinks and gitlinks are not automatically absorbed in this version. Preserve and report such staged entry changes explicitly with their paths and reasons. A new-file addition never becomes a guessed older-commit amendment. A feature history containing unchanged binary/other entries is not itself unsupported; unchanged content must replay losslessly. Detect names/encodings, filters or index states that cannot be handled losslessly and refuse before effects rather than reinterpret bytes or follow symlinks. Renames need not be inferred: safely reporting the participating entry changes as retained is sufficient.

5. **Prospective input and staging.** Without a staging option, the user's existing stage-zero index tree is the input and unstaged work is excluded. --all projects updates/deletions to tracked paths, retains already staged entries, and does not add untracked files. It must not reuse a broad add-all operation that includes untracked files. --patch uses the existing real interactive Git hunk-selection behavior against an owned staging view, preserving previously staged work; only accepted hunks join the prospective index. Rejected hunks remain unstaged. No hidden prompt to stage everything is added. Validate known source/protection conditions early, then the complete selected rewrite plan, before publishing staged input or beginning a rewrite. Incompatible options, missing required terminal input and declined confirmation retain the original index and worktree. Dry-run with --all projects the same prospective tracked input without publishing it. Merely preparing a plan cannot consume the real index.

6. **Inspection and preview.** Dry-run uses a preserving read-only path rather than ordinary mutation initialization/cleanup. It must preserve branch and metadata refs, both relevant raw indexes, working/untracked/ignored bytes, local PR/protection data, saved continuation and foreign locks. Avoid optional Git index refresh, external diff/textconv commands, hooks, editors, pagers, repository repair and cache deletion. Owned scratch data is permitted only outside user working paths and must be removed safely; this is not a promise about filesystem access times or universal filesystem immutability. Show each selected hunk's path and original destination branch/commit, all retained text hunks and unsupported entries with reasons, and mandatory replay branches. Report known mandatory blockers with a nonzero status instead of presenting the plan as executable. Distinguish hunk counts from retained entry counts; a staged new/binary file cannot disappear from the report. No-input and no-eligible-target previews return an explicit successful no-op description, with no invented application progress.

7. **Confirmation and noninteractive policy.** Ordinary interactive application displays the plan before asking once for confirmation. Decline or cancellation before application leaves original refs, index, work and metadata intact. --force bypasses only that confirmation. A noninteractive, quiet or closed-input application without --force fails clearly with a nonzero status and the required flag, before staging or mutation. This deliberately differs from the measured Graphite invocation that returned a successful implicit preview. Explicit dry-run is usable without --force and never asks for confirmation. --patch still requires supported terminal interaction even with --force; MCP cannot supply that interaction. No force flag overrides frozen/worktree/ref checks. With no eligible amendments, a confirmed/forced --all or --patch execution may publish only its explicitly requested staging selection and must say that nothing was absorbed; otherwise an ordinary no-op leaves existing input staged. The output must not call staging-only completion an amended commit or a rewritten stack.

8. **Complete participant plan and early protection.** Determine the changed target branches, all later own commits within each target branch, and every tracked descendant whose recorded base must advance, including the original checkout, descendants above it, and side arms of a fan-out. Unrelated/untracked refs remain untouched. Every mandatory rewrite must be editable and unoccupied outside the effective worktree; do not silently skip a frozen or occupied mandatory descendant. Read-only frozen/occupied anchors are allowed. Check the entire mandatory plan, intermediate checkout/replay file collisions, tracked/ignored/untracked work and expected refs before staging publication or the first amendment. A known unsafe plan is refused with original user and linked-worktree state intact. Recheck refs, fresh protection and worktree availability at relevant mutation/publication/resume checkpoints. These checks handle known blockers; arbitrary hook/external process changes are not a filesystem sandbox or an atomic transaction.

9. **Commit and stack preservation.** Amend each selected original commit, not simply the nominated branch's tip. Replay its later own commits and the saved mandatory branch ranges in parent-first order, including off-corridor descendants; do not flatten, squash, add permanent fixup commits or infer own ranges again from partially rewritten tips. Retain each existing commit's author identity/date and complete message/body/trailers and preserve own-commit order. Keep a selected commit even when its exact correction leaves it empty, retaining the branch identity rather than deleting it as a side effect. Existing commit signing and committer policy remain in force; new OIDs, committer metadata or signatures are expected and old signatures are not promised. Preserve branch names/logical parent names, local PR linkage and metadata not owned by the rewrite; update recorded bases to the actual new parents without resetting frozen status. Trunk and unrelated refs/trees remain unchanged. All mandatory branches must finish before reporting successful absorption. After a nonconflicting success the original checkout is restored; its committed tree equals its old tree with exactly the accepted staged hunks, while each replayed descendant keeps its own changes on the corrected ancestry. Do not assert that descendant tip trees are unchanged when the correction deliberately changes inherited content.

10. **Local work as a separate retained input.** Before changing commits, safely retain the prospective index tree, the remaining staged entries and the working-tree differences relative to that index, together with enough original state/ownership to restore them or recover from failure. After ordinary nonconflicting success, the restored index content equals the prospective index content: absorbed hunks are now in HEAD and no longer appear staged; the other input remains staged. Formerly unstaged changes remain unstaged and working file bytes, unrelated untracked/ignored files and user stash entries are retained. Raw index byte equality is an inspection/refusal requirement, not an application-success requirement. During a Git conflict, do not merge leftover user input into Git's resolution index or present its absence there as loss. Keep it in an identifiable owned recovery artifact and report its location and staged/unstaged roles. Restore it at a checked safe final point exactly once. Never overwrite newly created user/conflict/hook work to satisfy a restoration claim; if restoration cannot safely complete, fail with reached state and preserve the owned input. Any internal stash/index/worktree must be identified and cleaned only by proven ownership after verified restoration; never clear the user's stash list.

11. **Publication and reached-state reporting.** Separate read-only planning, local-work retention, commit rewriting/ref adoption, descendant replay and local-work restoration in the operation state. Reuse existing checked-ref, metadata, hook and replay mechanisms where they fit; add only the minimal absorb-specific plan/work-preservation support needed. A failed preflight has no staging or rewrite effects. A later failure can leave completed amendments or replays; distinguish confirmed completed work, the active operation and pending work, and do not print overall success. A ref or metadata publication failure must report actual saved branches/bases rather than imply rollback. No general transaction or global recovery framework is required. The retained input must not lose its only reference because ordinary context initialization or a no-rebase continue clears a legacy continuation record.

12. **Genuine conflict continuation.** Integrate a minimal optional absorb role with the existing continuation/replay lifecycle, preserving existing formats and operations. It records original departure, saved ranges and expected refs, selected pending/completed amendments/replays, and the owned input restoration checkpoint as needed for exactly-once progress. A genuine replay conflict returns nonzero with actual rebase/unmerged state intact and reports resolve, stage and continue instructions. Fresh-process continue resumes that replay and the remaining saved plan without repeating completed absorption or recalculating destinations from altered tips. Recheck expected refs, frozen status, worktree/file availability and rebase ownership before continue can stage with --all or advance. A refused continuation preserves staged resolutions and recovery/input artifacts. Successful finalization restores remaining work once and returns to the original checkout. No absorb job continues after MCP disconnect/cancellation under a new scheduler; existing MCP lifecycle limits remain authoritative.

13. **Hooks, abort and non-rebase failures.** Retain the established verification/no-verify scope and actual commit/replay hooks. Do not synthesize commits solely to bypass hooks; do not claim --no-verify suppresses every Git hook. Hook/editor/ref failures can leave different Git states. Inspect the actual active operation and report continue only when its prerequisites exist; a retained rebase directory alone is not proof of an unresolved content conflict. Without a continuable rebase, preserve reached commits, hook-created work and the owned input artifact, state what remains and print an actually executable manual recovery/restoration path using existing Git/Anthracite operations. That path must be exercised by the acceptance fixture. A raw rebase abort cancels only the active rebase, does not undo earlier amendments and must not discard retained user input. General automatic post-abort retry, an absorb-specific abort/undo command and rollback of arbitrary hook effects are not part of this feature.

14. **Compatibility and module boundaries.** Keep target planning, bounded rewrite/replay and retained-input recovery as cohesive responsibilities behind the public CLI, without a new generic rewrite framework. Existing branch-tip amendment and file-split flattening are not acceptable substitutes for interior-commit rewriting with author/message preservation. Existing generic restack skipping is not sufficient for mandatory participants. Extend continuation recognition, protection, completion recording and finalization only where the new optional role needs it; old recovery states remain readable and untouched by refused absorb calls. Strict inspection and early validation must avoid incidental ordinary-context continuation/PR-cache cleanup. Introduce no stored-stack migration, new authentication model or new MCP transport. Documentation describes bounded text support, explicit leftovers, real signatures/committer behavior and manual-recovery limits.

15. **User-facing output and agent delivery.** Normal progress identifies destinations, completed updates/replays and retained work. Quiet suppresses routine progress and successful no-op chatter but retains actionable errors, reached-state/backup information and conflict instructions. Help/completion expose absorb/ab, short flags, supported combinations, tracked-only --all, noninteractive --force, preview safety, protected participants and recovery limits. The existing run_an_cmd tool executes the same CLI build with literal args and explicit cwd; its established envelope and failure semantics are unchanged. Update the existing learning guidance only as needed to explain the newly supported command and its limitations. No fetch, push, remote PR/cache refresh or other GitHub action is implicit in a local absorb.

16. **Delivery and acceptance.** Implement this contract after ticketing in one implementation PR with linear history and retained upstream credits. Run the approved focused CLI cases locally on Node and an independently compiled native executable, affected existing controls, and one installed npm/MCP smoke. Only the existing cheap automatic CI may run after implementation publication. This specification task publishes documentation and an issue; it does not implement the feature, create implementation tickets or PRs, dispatch/rerun the full matrix, release/tag/build standalone assets, replace the global installation or change client configuration.

## Testing Decisions

The primary seam is the built public CLI in real temporary Git repositories. Use existing relation/cwd snapshots, frozen/worktree and file-collision fixtures, real patch/confirmation PTYs, hooks and structural replay/continuation fixtures. Add only small fixture support needed to prepare the declared histories. Do not add mocked engines, test-only command exports, an in-memory stack model or a private selector seam. One secondary smoke crosses the already established real stdio MCP boundary using an isolated installed npm package; it is not a protocol/lifecycle matrix.

Good tests derive expected content and history from declared original commits, staged/unstaged input and deliberate conflict resolution, using independent Git observations or a separate explicit Git control. A candidate renderer, preview or private selection helper cannot prove its own correctness. Inspect exact target commit trees, commit order, full author/message data, branch ancestry and public tracking/PR identity; check refs, both relevant indexes, files and opaque recovery data on refusal. Never compare rewritten OIDs for equality with old OIDs as a success requirement. Check no-effect guarantees separately from reached-state guarantees.

## Out of Scope

- Automatic absorption of new files, binary content, whole-entry deletion, rename/copy identity, mode/type changes, symlinks/gitlinks and unsupported merge histories. Safe retention/refusal and complete reporting remain in scope.
- Semantic/AI ownership, manual destination selectors, pathspec-selection UI, custom commit messages, history flattening, new branches/PRs or implicit auto-staging prompts.
- Preserving old commit OIDs/signatures, universal unchanged descendant trees after corrected inherited content, or guessing how to repair a stale downstack corridor.
- General undo/abort, transactional rollback, a universal history-rewrite framework, a background/durable job service, automatic retry after arbitrary hook failure or lossless rollback of external effects.
- Global stash cleanup, foreign process/lock deletion, arbitrary filesystem containment, full operating-system certification or new cross-platform path machinery.
- Fetch/push/submit/review/merge, live GitHub PR fixtures, Graphite authentication/backend services, repository format migrations or resetting frozen status.
- New MCP tools, protocol changes, client configuration, a new MCP cancellation test matrix or a second implementation of CLI semantics in the server.
- Implementation or ticket creation in this specification task; full CI dispatch/rerun, releases/tags/assets, global installation or unrelated deferred parity work.
