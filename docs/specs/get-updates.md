# Scoped remote updates, checkout control and restacking for get

## Problem Statement

Anthracite users cannot refresh a locally present stack with the same useful controls observed in Graphite 1.8.6. In released Anthracite 0.5.1, get follows PR bases from trunk to a target, always attempts a final target checkout and has no automatic descendant-restack phase. Fetching a parent leaves locally tracked successors behind. After a parent PR lands and another PR changes base, forcing get can update the feature head without advancing trunk or providing a coherent parent-update workflow.

Developers and agents need predictable remote-update selection, a way to retain their checkout, and explicit control over maintenance of local descendants. Expanding selection must preserve unpublished work, frozen status, worktree protection and usable conflict recovery. Cleanup consent must not become permission to reset trunk.

The measured reference is Graphite **1.8.6**. The Anthracite source baseline is released **0.5.1**, commit `5f76186bcfd2ee0952b9cb48bab1ddf94f00c3c5`. Historical runtime observations compare Anthracite 0.5.0; the evidence record establishes the unchanged get implementation in 0.5.1. This specification defines intended Anthracite behavior, including deliberate safety choices; it does not certify complete Graphite parity.

## Solution

Make get a bounded remote-update operation with separate remote-refresh and local-maintenance selections. For a feature target, refresh its PR-derived ancestor chain and, by default, eligible locally tracked descendants of that target. `--downstack` excludes descendant remote refresh. Neither mode discovers remote-only descendants.

Restack by default after remote updates, with `--no-restack` to retain local histories and report pending maintenance. Checkout the target on successful completion by default; `--no-checkout` restores the original physical checkout after all phases complete. Safely advance trunk by fast-forward where the feature update needs it, and accept validated PR-base changes without requiring feature overwrite when the incoming head is identical or a fast-forward. Get does not delete branches.

For example, in `main → base → child → tip`, getting base normally refreshes eligible local child and tip heads too. Getting child with downstack enabled refreshes base and child, not tip or the sibling arm below base. If changing base makes that sibling require local maintenance, the maintenance selection is disclosed separately; the sibling is not fetched merely because it needs replay. An independent stack directly below trunk remains outside the operation.

## Implementation Decisions

1. **Target and compatibility.** Keep get and g, the optional branch argument, all-digit PR-number interpretation, existing current-branch default, force/-f and unfrozen/-U. Resolve omitted targets from the physical checkout, not a continuation override. A detached checkout requires an explicit target. Resolve against the configured repository and single trunk, preserving the current trunk-target no-op rather than interpreting trunk as an all-stacks selector. Reject unsupported or invalid inputs before application. Do not introduce PR-URL syntax, additional short flags, a preview command or configurable aliases.

2. **Boolean interface and intentional defaults.** Add downstack, restack and checkout controls using the CLI's ordinary boolean/negation semantics. Downstack defaults false; restack and checkout default true. The negative restack and checkout forms are supported and documented. These are intentional behavior changes from 0.5.1: existing local descendants may receive remote updates and local histories may be replayed by default. Downstack plus disabled restack preserves the earlier remote-selection/replay scope, but does not disable this feature's safe trunk fast-forward or promise byte-identical historical execution.

3. **Explicit graph selections.** Define the downstack chain as the validated PR-base chain from configured trunk to resolved target. The remote-refresh selection adds existing tracked descendants of the target unless downstack is enabled. Do not add siblings merely because an ancestor belongs to that chain. Deduplicate by exact branch identity and order selected parents before children, with a stable order between peers. Every node retains its own validated parent; a DFS array must never imply that the previous sibling is its parent. Cycles, inconsistent repository/head identities and an untraceable required chain fail before application.

4. **Refresh eligibility and local-only work.** The target and its required PR chain retain the existing requirement for a traceable remote source. For an added local descendant with no stored PR association and a confirmed normal absence of a PR, retain its head as local-only work; it may still need maintenance. Do not require its publication or silently use another PR. Explain that its remote refresh was skipped. An associated PR whose required source cannot be fetched is a failure, not a local-only shortcut. Authentication, rate-limit, transport, malformed responses and mismatched identities fail distinctly. A closed or merged association never grants deletion permission; a still-fetchable valid source can be refreshed under the same checks, while a missing required source is reported without cleanup.

5. **Snapshot before application.** Resolve identities, fetch the required remote snapshots and compute remote updates, parent changes and prospective maintenance before applying user-facing local changes. Fetch/cache/tracking-ref writes may occur while discovering a blocker; do not promise a completely write-free transaction. Retain the fetched OID intended for each selected branch rather than treating a shared last-fetch ref as every node's source. Pin PR identity/base information consistently to the fetched plan; a material inconsistency requires refusal/replanning before application. Remote movement after that snapshot does not authorize fetching or applying additional branches automatically.

6. **Known blockers and fresh checks.** Validate dirty tracked state, collisions, active operations, foreign/owned recovery, local divergence requiring a decision, worktree occupancy and required participant editability before application. Collect required existing interactive reconciliation choices before beginning local application; cancellation aborts that plan. Recheck relevant local heads, parents, freeze state and worktree occupancy immediately before their writes and during guarded hook-sensitive publication. A changed plan is not silently expanded. Existing Git hooks remain enabled. No general multi-ref transaction, automatic stash or rollback is introduced.

7. **Trunk advancement.** For a non-trunk target, inspect the configured remote trunk and advance local trunk only when it is identical or a fast-forward. If local trunk is ahead of or diverged from remote, refuse the planned advancement while preserving its commits; feature force does not override this rule, including interactively. Missing remote trunk or an unsafe/occupied trunk update fails through the normal guarded path. Updating trunk does not authorize replay of every independent trunk stack, cleanup, remote publication or foreign worktree modification. Trunk-target no-op behavior remains separate.

8. **Feature application and changed PR bases.** Ordinary selected feature heads are retained when identical and updated by fast-forward when possible. When the same validated PR now names a different valid parent, permit a guarded metadata parent transition alongside an identical/fast-forward feature update without requiring overwrite. The former parent and its unrelated children remain tracked and undeleted. A divergent head, locally untracked collision or unverified parent relationship still requires the existing explicit reconciliation/overwrite contract or refuses. Force applies only to eligible selected feature sources; it never authorizes trunk reset, deletion, unfreezing, collision loss or replacement of local-only maintenance participants.

9. **Two phases and maintenance closure.** Apply the planned incoming feature updates before automatic maintenance, so a descendant is not first replayed locally and then mistaken for divergence from its still-pending remote snapshot. The maintenance selection contains selected branches needing repair against their resulting parents and affected tracked descendants of changed selected feature heads/parent relationships. Follow dependencies through shared ancestors: a sibling outside the remote-refresh selection may need local replay if its shared feature parent changed. Do not include an independent trunk stack merely because trunk advanced. Disclose affected maintenance participants separately from remote-refresh participants before their replays.

10. **Restack authority and content.** With restack enabled, use the existing local replay contract to retain each surviving branch's own commits, authors, complete messages and resulting changes, dropping already-applied parent patches through ordinary Git behavior. Maintain valid parent metadata. With restack disabled, do not perform automatic maintenance replays; retain the affected heads and report pending restack work. A rebase explicitly chosen to reconcile a divergent selected feature remains a separate existing permission and is not an automatic maintenance replay. Get performs no pushes or GitHub writes in either mode.

11. **Frozen branches and imports.** Preserve current inbound-update permission and existing frozen status, including fresh freezes introduced by hooks. Preserve ownership-verified editable imports and conservative frozen imports when authorship cannot be verified; optional identity verification failure must not make a new branch editable. Preserve explicit unfrozen import behavior without changing existing branch status. Automatic restack follows existing frozen-anchor policy: do not locally rebase a frozen branch, and use its retained head as an anchor where the existing contract permits editable descendants to proceed. Name skipped/unreplayed frozen work. If a required local parent/replay change cannot safely proceed with that anchor unchanged, refuse rather than unfreeze or silently omit mandatory work. Success must not claim every branch is fixed when protected/deferred work remains.

12. **Local work and worktrees.** Retain the current conservative refusal of staged/unstaged tracked work before stack-changing application; broader dirty-worktree support is excluded. Preserve untracked and ignored files through existing collision checks, including force. Do not promise dirty no-op/final-switch success beyond existing safe behavior. Check every physically affected update, checkout and replay against occupied worktrees; an unrelated occupied branch is not a blocker. Do not copy Graphite's trunk-worktree exception or modify another worktree's files. Known blockers refuse before the local changes they would prevent; a hook-created or otherwise late blocker reports actually reached changes.

13. **Final checkout.** Record the physical starting branch or detached OID before any intermediate checkout. On complete success, checkout enabled selects the resolved target; checkout disabled restores that original branch, or the exact original detached OID. A surviving original branch may have received an authorized update, so this is restoration of checkout identity, not reset to its old OID. It does not promise no intermediate checkout. If the original ref disappears, a checkout collision arises or final checkout fails, report nonzero with reached updates and the actual checkout; do not recreate/reset refs or pretend restoration succeeded. A real replay conflict stays at its reached Git recovery state until resolution.

14. **Owned continuation.** Reuse ordinary Git rebase recovery and an continue/cont. Preserve enough optional get-owned intent to distinguish reconciliation from maintenance, exact repository/target, each remaining node's parent and pinned fetched source, selections, remaining replay work, import decisions and final-checkout policy. Keep pinned fetched objects reachable for the owned operation and remove only its owned temporary state after confirmed completion. Resume from a fresh process without reinterpreting the graph as a linear chain or rereading new command defaults. Recheck active and remaining required participants before continue-all stages files or advances work. Finishing continuation performs the saved final-checkout policy only after all owned phases complete. Preserve legacy continuations without new get intent and unrelated saved operations; no global migration or generic recovery replacement.

15. **Failure, interruption and abort.** A late failure reports confirmed updates/parent changes/replays, the active or failed phase and pending work. Retain actual Git conflict state and staged resolutions, with the original project directory and existing continuation instructions. Do not claim rollback of completed remote imports or local rewrites. Raw Git abort cancels its current rebase only; stale, foreign, incompatible or aborted get intent must not be consumed as a live operation, clear unrelated recovery, blindly stage files or advance a queue. Retain guarded inspection/manual-recovery guidance where automatic continuation cannot be verified. Cancellation and MCP timeout inherit existing owned-process supervision; no new promise of atomic cancellation is made.

16. **Errors and reporting.** Return zero only for a completed declared workflow, including explicit explained skips permitted by import/frozen policy; return nonzero for invalid input, blockers, conflicts, inconsistent/uncertain effects or failed final checkout. Report pending maintenance when restack was disabled or frozen policy retained an anchor. Never equate exit zero with universal freshness or complete restacking. Preserve quiet/noninteractive conventions while keeping essential failure/progress/recovery diagnostics visible. Effective noninteraction launches no prompts, editors, browsers or pagers. No interactive choice may be inferred from elapsed time.

17. **Reuse without expanding sync.** Put graph-aware fetch/application and replay orchestration behind a bounded shared operation with explicit target nodes, parent/source snapshots and separate overwrite/trunk/replay authority. Extend the existing get command, remote-update engine boundary, continuation handling, help/completion, user documentation and MCP learning. Reuse existing guards and replay machinery rather than introducing a parallel stack engine or a generic transaction framework. The later sync feature may call the same operation with its own selection and defaults. This delivery must leave current sync refresh/default/force/cleanup behavior unchanged, including the released B02 correction.

18. **Delivery and compatibility guidance.** Describe default local-descendant refresh, default restack, safe trunk advancement, final-checkout control and maintenance outside downstack refresh scope in help, completion, learning and release guidance. Keep existing options and new negative forms consistent across get/g, explicit cwd and MCP literal arguments. Preserve legacy metadata/settings and interrupted supported operations. Document that a pending new get workflow must finish before downgrading; older releases are not certified to resume its graph-aware intent. Existing tests that intentionally asserted old default selection or no replay should become explicit compatibility-mode controls rather than being deleted or presented as unchanged defaults.

## Testing Decisions

The owner approved the primary seam: the **public CLI process**, real temporary Git repositories and bare remotes, with only external GitHub responses controlled. Assert actual refs, commit ancestry/content, parent relationships, physical checkout, index/work files and recovery state independently of the operation's internal plan. Do not mock the engine, fetch/update/replay helpers or continuation implementation. The gh fixture must distinguish normal absence from errors and reject unsupported calls.

Prior art is the existing [get fast-forward acceptance](https://github.com/danielbaars/anthracite/blob/v0.5.1/apps/cli/test/commands/get_fast_forward_cli.test.ts), [frozen get acceptance](https://github.com/danielbaars/anthracite/blob/v0.5.1/apps/cli/test/commands/get_frozen_cli.test.ts), [import-default acceptance](https://github.com/danielbaars/anthracite/blob/v0.5.1/apps/cli/test/commands/get_import_defaults_cli.test.ts), structural continuation/worktree controls and the real stdio MCP client. Extend these seams, not a new test framework. Real terminal choices use the existing PTY boundary. Isolate Git configuration so user rebase settings cannot rewrite fixture refs outside Anthracite.

## Out of Scope

- Remote-only successor discovery, remote-upstack, Graphite submission/indexing, Graphite credentials and hosted-service emulation.
- Get cleanup/delete-all, removal of former parents, remote branch deletion, PR writes, pushes or automatic publication of local work.
- Multiple trunks, all-trunk/all-stack selectors, alternate providers/remotes and general repository configuration.
- The sync feature-head refresh extension, new sync cleanup consent, changes to sync restack defaults or reinterpretation of its existing force option.
- Broad dirty-worktree tolerance, automatic stashing, implicit local resets/unfreezing, forced worktree access or Graphite's trunk-worktree exception.
- A generic undo/abort/rollback system, recovery of every interrupted write, a multi-ref transaction engine or global continuation migration.
- New MCP tools, authentication schemes, exhaustive platform/shell testing, unrelated maintenance, publication/installation of an implementation or release assets.
