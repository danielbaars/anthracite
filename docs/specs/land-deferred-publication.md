# Defer publication of later landing targets

Scope and the public-process test boundary approved on 9 November 2026. This is a proposed change to Anthracite, not shipped behavior or acceptance of an optimized implementation.

## Problem Statement

Landing a stack repeatedly publishes branches that will be rewritten again before their own merge. On the retained seven-PR synthetic stack, current main performs 21 feature-update pushes, seven deletion pushes and 21 PR base/footer edits. The top branch is published six times. These intermediate updates can trigger unused beta/preview workflows and repeat pre-push hooks.

The [measured baseline](../verification/land-push-amplification-2026-11-09.md) is merged main `a3c9f705`, including PR #163's required-check fix. Optional checks no longer need to block landing, but their underlying publication triggers still exist.

## Solution

For new landings, keep current local maintenance, but publish only the next selected merge target when it needs preparation for its own merge. Leave later targets' remote heads and PR base/footer edits deferred until their turn. Continue handling surviving branches outside the merge set with the existing eager policy.

Disclose deferred work in the plan and saved progress. Preserve every required readiness and publication guard, and keep existing saved landings on their original eager publication schedule. No new CLI option is needed.

## User Stories

1. As a developer, I want a later PR published only when its merge approaches, so that intermediate restacks do not repeatedly trigger unused publications.
2. As a developer, I want required pre-push hooks to run on real pushes, so that fewer pushes do not weaken checks.
3. As a developer, I want the next PR's exact reached head and trunk base verified before merging, so that deferral cannot merge stale code.
4. As a developer, I want required checks and approvals assessed on the intended published head, so that old green results cannot authorize a new head.
5. As a developer, I want local replay and conflict detection to retain their current order, so that a distant conflict is not silently moved past more merges.
6. As a developer, I want plans to distinguish deferred publication from a blocker, so that I understand why local and GitHub heads can temporarily differ.
7. As a developer, I want dry-run and confirmed resumption to show the same fresh plan, so that the effects I approve match current state.
8. As a developer, I want interruptions to retain all publication obligations and leases, so that restarting neither overwrites others nor loses pending work.
9. As a developer, I want confirmed merges and completed pushes recognized on retry, so that effects are not blindly repeated.
10. As a developer, I want existing PR descriptions, roles, draft state and unrelated body content retained, so that later reconciliation changes only the intended base/footer.
11. As a developer, I want non-target survivors and unpublished branches handled within their existing scope, so that an optimization does not expand publication or rewrite independent work.
12. As a developer, I want my already pending landing to retain its original publication schedule, so that installing an update does not reinterpret unfinished work.
13. As an agent user, I want the same plan and safeguards through MCP, so that automation can identify deferred work without bypassing the CLI.

## Implementation Decisions

- **Bounded scheduling change:** new landings defer remote publication of later merge targets only. After each confirmed merge, retain the existing affected local reparent/replay pass. Prepare the immediately following unmerged target and perform existing non-target survivor maintenance before cleanup advances the operation. Do not publish more distant merge targets merely because their local heads changed.
- **Base safety before cleanup:** publish and reconcile the next target's PR base to trunk before deleting its landed parent ref. More distant targets retain existing parent refs until that parent is itself landed and they become next. Never depend on assumed GitHub auto-retargeting. Already externally merged targets remain subject to existing confirmed-result/cleanup-only guards and are not republished to satisfy a count.
- **Coalesce pending work:** retain the latest reached local head separately from the last verified published head and captured lease. Further authorized local replay may replace a deferred target's pending reached head; publish its latest reached head when due. Deferral is never evidence that a remote change occurred or was authorized. Recognize an already matching owned remote head without another push.
- **Couple publication and PR reconciliation:** defer a later target's head push and its base/managed-footer reconciliation together. When due, read the existing PR freshly, verify its pinned identity/state/head and remote lease, publish under the ordinary hook/frozen guards, reconcile against current descriptions, then verify the result. Existing titles, draft state, roles and unrelated body content remain protected. No PR creation or broad submit is introduced.
- **Readiness remains fresh:** immediately before each merge, require the intended local/remote/PR head agreement, trunk base/ancestry, current policy, approvals and required checks/publisher evidence. Keep existing bounded required-check waiting, optional-check warnings, unknown-policy refusals and protection against changed identities. A later target's old checks do not establish readiness for its pending local head. An unknown later reached-head readiness caused solely by deliberate deferral must not block progress on a fully verified next target; unrelated real blockers retain existing authority.
- **Explicit durable schedule:** new landing records use version 2 to identify deferred-target scheduling and retain enough per-target publication/PR reconciliation state to distinguish deliberate deferral, due work, completed work and uncertain effects. Record intent before effects and preserve existing record ownership/concurrent-write protections. Unknown or contradictory state refuses before further effects. No general stack metadata migration is needed.
- **Legacy compatibility:** parse version-1 landing records and continue their eager publication schedule, including partially completed mandatory maintenance. Do not convert them implicitly or treat an interrupted eager push as deliberate deferral. Both versions use the current readiness policy; legacy scheduling does not restore the old all-checks gate. Document that pending version-2 landing must be completed before downgrading to a CLI that cannot read it.
- **Honest inspection and recovery:** fresh and saved plans identify later branches whose publication is deferred until their merge preparation. Default output uses branch/PR names and next actions; debug retains OIDs and operation diagnostics. Do not label the whole remaining stack as freshly ready when later reached heads are not yet published. Dry-run and pre-confirmation inspection remain preserving. On failure or interruption, disclose confirmed merges, reached local work and pending publication/base/footer work; never repeat an uncertain merge or clear recovery with due work outstanding.
- **Unchanged local/survivor boundaries:** keep early local replay, parent-before-conflict persistence, owned continuation and original affected-scope selection. `continue` remains local-only; explicit land resumes remote work. Non-target published survivors retain eager publication; local-only branches stay unpublished; independent trunk stacks remain untouched. Preserve the baseline survivor-scope limit: a sibling maintained after its affected ancestor merges is not newly promised another replay onto final trunk.
- Update the landing guide, command help where relevant and existing MCP learning in English. Keep this within one implementation PR. Do not change repository workflows, add an ignore-checks mechanism or bypass hooks.

Inspect actual refs, files, authors/messages, staging and saved bytes rather than private scheduler objects. No new internal test interface is required.

## Out of Scope

Deferring local replay or changing conflict timing; deferring non-target survivor publication; restacking every survivor onto final trunk; changing branch selection, merge method or cleanup scope; batching deletions; bypassing pre-push hooks; cancelling Actions or changing beta/Pages workflows; new configuration/CLI toggles; general recovery redesign; repair of unrelated baseline landing defects; live GitHub fixture mutations; changes to frontend-packages, other user projects or the active installation; CLI release publication.

No CI runs during specification. The full CI matrix remains off. Later implementation may use ordinary CI within the existing budget; this specification starts no workflow.

## Further Notes

The [research report](../verification/land-push-amplification-2026-11-09.md) and [source constraints](../verification/land-push-deferral-source-analysis-2026-11-09.md) were committed and pushed as `b4efb2cd` with unchanged raw captures. They measured current behavior only. Six versus 21 updates becomes an acceptance target for the controlled fixture; actual Actions-run reduction, billing and live GitHub's intermediate presentation remain unmeasured. This does not promise that all workflows disappear or that GitHub universally requires six pushes.

The broader baseline recovery assertions and final-trunk survivor limitation remain explicitly separate. This bounded optimization must preserve existing protections and scope without silently absorbing those other repairs.
