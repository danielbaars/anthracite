## Problem Statement

The owner increasingly operates Anthracite through coding agents. Today each agent must discover the CLI, construct shell commands, interpret terminal output and learn the stack workflow separately. Anthracite has no MCP entry point, despite already providing the stack operations, non-interactive policies and recovery behavior that an agent needs.

Graphite 1.8.6 exposes a local MCP server with two tools: `run_gt_cmd` and `learn_gt`. A real stdio probe establishes discovery, learning, command execution and continued availability after a CLI failure. Its execution tool returns text, including an error description for a failed command, without separate exit-status fields or an explicit `isError` field in the measured failure. Anthracite should offer the same useful two-tool shape while making results and process behavior explicit.

The accepted source baseline is Anthracite `e201e0629c547f3c88845ab37a9bf64555f21c19`, installed as `0.1.1-dev.20261027173714`. A direct `an mcp --no-interactive` probe exits 1 with an unknown-command diagnostic. This specification adds an agent-facing transport around that CLI; it does not promise complete Graphite MCP or service parity.

## Solution

Provide `an mcp` and `anthracite mcp` as local stdio MCP servers bundled into the existing executable. An MCP client can discover two tools, learn the supported Anthracite workflow and invoke the same build's CLI with an argument array, an explicit working directory and an explanation.

`run_an_cmd` returns separate stdout, stderr and process status in a stable result envelope. `learn_an` supplies concise English guidance that respects the user's repository instructions and publication approval rules. Existing stack behavior, frozen/worktree protections, Git hooks, GitHub CLI authentication and conflict continuation remain authoritative.

The server never turns a tool call into an interactive terminal session. It preserves the actual outcome of each command, keeps protocol stdout clean, and bounds execution and captured output. Client cancellation, timeout and shutdown stop owned work without pretending that Git changes were rolled back.

The owner approved one public testing boundary and approximately 12–15 focused scenarios, including genuine conflict recovery, process lifecycle and a controlled submit adapter. The implementation must satisfy the fifteen named scenarios below on Node and a separately compiled native binary. Only the existing cheap automatic CI is allowed; the full matrix remains excluded.

25. As an agent user, I want prompts, pagers and editors disabled, so that commands cannot hang waiting for terminal interaction.
26. As an agent user, I want missing required choices explained, so that I know which selector or metadata to supply next.
27. As an agent user, I want quiet and debug options to preserve MCP framing, so that ordinary output policy cannot break the connection.
28. As an agent user, I want a rebase conflict reported with its partial state preserved, so that I can resolve it intentionally.
29. As an agent user, I want to reconnect and continue a real interrupted stack operation, so that recovery does not depend on an in-memory session.
30. As an agent user, I want a submit call to reuse existing credentials and CLI behavior, so that a separate MCP account or Graphite backend is unnecessary.
31. As a repository owner, I want MCP learning and discovery never to stage, commit or publish automatically, so that connection itself is not authorization.
32. As an agent user, I want complete ordinary output including trailing newlines, so that the adapter does not rewrite the CLI's data.
33. As an agent user, I want large supported output delivered completely, so that pipe buffering does not truncate a successful result.
34. As an agent user, I want output-limit failures explicitly marked, so that partial output cannot be mistaken for a complete success.
35. As an agent user, I want a bounded configurable command timeout, so that an unavailable external tool cannot block the server forever.
36. As an agent user, I want request cancellation to stop owned CLI work, so that cancelling has an observable process effect.
37. As an agent user, I want cancellation of queued work to prevent its execution, so that an abandoned command cannot start later.
38. As an agent user, I want late or unknown cancellation handled harmlessly, so that a race cannot cancel another request.
39. As an agent user, I want EOF and server termination to stop active and queued work, so that client shutdown does not leave ordinary CLI descendants running.
40. As a repository owner, I want interruption cleanup limited to proven owned processes and locks, so that unrelated work is preserved.
41. As an agent user, I want interrupted operations described without a rollback promise, so that I inspect actual Git state before retrying.
42. As an agent user, I want command help and completion to describe the server options, so that configuration agrees with execution.
43. As a maintainer, I want the same public scenarios on Node and native, so that the packaged server matches development behavior.
44. As a maintainer, I want existing CLI fixtures reused, so that this feature verifies the adapter rather than retesting every engine operation.
45. As a maintainer, I want measured Graphite behavior separated from Anthracite decisions, so that deliberate improvements are not described as reverse-engineered parity.
46. As the repository owner, I want bounded local validation and cheap CI, so that this feature does not restart the expensive full validation matrix.

## Implementation Decisions

1. **Public interface and transport.** Register only the new root command `mcp`, available through both installed executable names. Its normal execution starts a persistent stdio server; it is not an alias for an ordinary Git command. Help, version and completion remain ordinary CLI documentation requests and exit without starting a session. Do not initialize a repository, repair metadata or authenticate during server startup, initialization, tool listing or learning.
2. **Protocol support.** Use an actively maintained official MCP TypeScript SDK compatible with the release runtime and pin the selected dependency in the lockfile. Negotiate at least protocol versions `2024-11-05` and `2025-11-25`. Identify the server as `anthracite` with the bundled package version. Advertise a static tools capability and exactly `run_an_cmd` and `learn_an`; do not advertise resources, prompts, sampling, elicitation, background tasks, dynamic tool-list changes or HTTP transport. For clients supporting tool annotations, classify learning as read-only/idempotent and execution as potentially destructive, non-idempotent and open-world. These are hints, not authorization. Follow SDK protocol handling for unsupported versions, malformed JSON-RPC and unknown methods/tools.
3. **Runtime feasibility is an implementation gate.** The current application uses CommonJS, Node 24.19.0, TypeScript 4.7 tooling and Bun 1.3.14 compilation. The published SDK survey identifies runtime and CommonJS exports, not compiler compatibility or a successful bundle. The first implementation slice must prove server/client imports, no-emit checking and a compiled stdio handshake before expanding the workflow. A necessary minimal compiler/declaration compatibility adjustment belongs in that slice and must be documented and checked; wholesale lint, framework, module-system or testing migrations are excluded. Do not hand-roll a parallel MCP protocol to avoid this gate.
4. **Execution input.** `run_an_cmd` accepts an object containing exactly three required fields: `args`, a nonempty array of strings; `cwd`, an absolute existing directory; and `why`, a nonempty explanation. Reject wrong types, extra fields, empty/whitespace-only explanations and NUL characters before spawning. Preserve individual argument strings; do not shell-parse, concatenate, interpolate or expand them. `why` is explanation metadata, never a CLI argument, shell fragment, authorization token or instruction for automatic follow-up work. It need not be persisted or echoed into repository configuration.
5. **Directory authority.** Resolve the supplied cwd per request and use it as that child's working directory. Never change the long-lived server's cwd or a shared process environment for a request. An explicit CLI cwd option that the existing preprocessor would consume must resolve to the same real directory or be refused before execution. Preserve the existing literal-argument and raw-Git boundaries; do not invent a second general CLI parser or fix unrelated parser behavior. Existing directories outside Git remain valid for commands such as version/help; repository-requiring commands report their normal CLI failure there. Paths containing spaces, Unicode or symlinks must not redirect another request.
6. **Reuse the executable boundary.** Execute the same build's CLI in a separate child, with closed stdin and separately captured stdout/stderr. A Node server launches its current runtime plus its fixed entry point; a native server launches its own compiled executable without a development entry-point argument. Resolve this identity before request-specific cwd selection. Do not resolve `an`, `ch` or `gt` through PATH or accept a caller-selected executable. Existing registered aliases, passthrough routing, configuration, hooks and credentials retain their CLI meanings. This generic tool is conservatively classified as capable of mutation and external effects; it is not a shell or filesystem sandbox.
7. **Non-interactive execution and recursion.** Force the existing Anthracite non-interactive policy for child calls independently of inherited terminal settings and explicit interaction options. Do not enable a PTY, supply prompt answers or launch Anthracite editors/pagers. Commands requiring choices must fail through their existing diagnostics. Reject attempts to start another MCP server through `run_an_cmd`, including the effective command after ordinary CLI prefixes; literal occurrences inside a message are not recursive commands. Documentation-only MCP help/version requests remain allowed when the existing parser classifies them as documentation rather than server startup. Raw Git passthroughs retain their own semantics, closed stdin and the lifecycle limits; arbitrary user hook/credential-helper behavior is not reimplemented or certified.
8. **Stable result envelope.** Return one MCP text-content item whose text is a JSON object. Always include `status`, `stdout`, `stderr`, `exitCode`, `signal` and `truncated`; wrapper errors also include an actionable `message` string. `status` is one of `success`, `cli_error`, `invalid_input`, `spawn_error`, `timeout` or `output_limit`; exit code and signal are nullable. Set MCP `isError` false only for a normally completed zero-exit command with full output. A nonzero child exit is `cli_error` with its actual code; a signalled child is a CLI error with the observed signal unless an already accepted timeout/output limit caused termination. Validation and launch errors have null exit code/signal unless a child actually ran. Preserve captured CLI stdout/stderr rather than inventing a CLI exit code. Text JSON is the stable cross-version representation; additional structured MCP output and domain-specific stack JSON are outside this first contract.
9. **Protocol errors versus tool failures.** Unknown methods/tools or invalid JSON-RPC remain protocol errors. Valid `tools/call` requests with invalid tool arguments or failed CLI execution return an error tool result using the envelope above. A CLI failure must not terminate the MCP session. Diagnostics about the server itself go only to stderr; child diagnostics go inside that call's result. Quiet never suppresses protocol responses, and debug never adds plain text to protocol stdout. Decode CLI output as UTF-8 without ANSI stripping, whitespace trimming, line-ending normalization or synthetic trailing newlines; binary-output fidelity is not promised.
10. **Learning and authority.** `learn_an` accepts absent arguments or an empty object, rejects extra arguments and returns concise maintained English text. Cover stack/trunk/upstack/downstack, explicit cwd, inspection, explicit staging through the user's normal tooling, create/modify/restack, frozen/worktree refusals, conflict inspection/resolution/continue and deliberate submit. Use real supported commands and distinguish Anthracite from Graphite authentication. Tool descriptions and learning are guidance, not authority to override higher-priority user/repository instructions. Do not require a particular branch-before-code ordering, infer permission to stage/commit/submit from connection or discovery, force a new approval protocol, or assume public PR metadata from the first commit. Preserve the owner's existing metadata/publication approval workflow in the guidance.
11. **Credentials and existing state.** Inherit the existing command environment and GitHub CLI credential mechanism; no Graphite token, additional MCP account or automatic login is introduced. Discovery and learning require no credentials. The wrapper adds no repository metadata format, migration, PR mutation, automatic init, status refresh, repair or cleanup. Inspections retain the direct CLI's existing bounded cache behavior rather than promising that every old cache is immutable. Frozen and worktree guards, hooks/verification, partial operation state and continuation formats remain the CLI's contracts.
12. **One active command per server.** Queue execution requests in arrival order and run at most one CLI child at a time for this first version. Discovery/learning/protocol cancellation must remain responsive while a child is running. Each queue entry retains its own request ID, arguments and cwd. Cancellation removes queued work without spawning it. Only release an execution slot after its child/group cleanup has completed. This avoids a new cross-repository mutex system; separate server instances continue to rely on existing CLI concurrency guards.
13. **Execution limits.** Add MCP-command-only `--command-timeout-ms`, default `300000`, accepting integer values from 1 through `3600000`. The deadline begins when the child is spawned, not while waiting in the queue. Add `--max-output-bytes`, default `1048576`, accepting integer values from `1024` through `16777216`; it bounds the combined raw stdout/stderr captured for one child. Reject malformed/out-of-range server settings before starting the transport. The first accepted stop reason wins. On timeout or output overflow, stop owned work, wait for cleanup and return `isError: true` with `timeout` or `output_limit`. Retain a bounded UTF-8-safe prefix; mark output as truncated when anything was omitted. Ordinary output below the limit, including a 96KiB subject and its ancestry tail, must be complete. These are Anthracite decisions, not measured Graphite defaults.
14. **Cancellation, EOF and signals.** Honor MCP cancellation for active and queued execution requests. On accepted active cancellation stop owned work, free the queue slot after cleanup and omit an ordinary result for that cancelled request; tolerate late-completion races as the protocol permits. Unknown, malformed or already-completed cancellation notifications must not affect another request. EOF/client disconnect, server SIGINT and server SIGTERM stop admission, discard queued executions and interrupt active owned work before exit. Do not create a durable job, retry a failed mutation or continue a queue after the client disconnects. Shutdown has no success/rollback claim for a partially executed command.
15. **Owned-process cleanup and lock ownership.** On supported macOS/Linux hosts launch each CLI child in an owned process group. Prefer SIGINT so the existing CLI can release its own lock; allow at most two seconds, then SIGKILL remaining owned group members and reap the child. Keep an internal cleanup watchdog; if cleanup cannot be established, report failure on stderr and stop the server rather than starting another mutation. Never kill by global process name or affect unrelated processes. Any necessary adapter lock cleanup is restricted to Anthracite's cache lock whose recorded owner matches the just-terminated child after owned work has stopped. Preserve pre-existing/foreign locks, Git lock files, staged resolutions and continuation data. Forced termination can leave Git state requiring inspection/manual recovery; no transactional rollback or containment of deliberately detached third-party daemons is promised. Windows process-tree support and cross-platform certification are excluded from this first slice.
16. **Preserve recovery across connections.** A normal rebase conflict is a CLI error result, not cancellation. Do not abort it, unfreeze branches, clear continuation or retry automatically. The owner can resolve files using ordinary tooling and call `continue` through a newly started MCP session. Stopping the MCP server does not erase a completed command's or an existing conflict's recovery data. Later diagnostics must describe the actual reached state, including any earlier commits/parent updates.
17. **Modules and discoverability.** Keep the new command/transport registration, bounded child-execution adapter and maintained learning text separate from the existing engine. Share the existing executable identity, parser and interaction policy where appropriate; any small prefactoring belongs inside this feature. Help/completion must expose `mcp` and its two server options. Document a generic local stdio client configuration using the installed executable and `mcp`, required per-call arguments, result semantics, supported host scope, limits and interruption behavior. Do not modify the owner's agent configuration or install/release a new global binary as part of implementing this specification.
18. **Delivery.** Implement this feature in one integration PR after ticketing. Keep history linear and retain upstream credits. Run the agreed focused tests locally on Node and native with source/binary identities; allow only the existing cheap automatic CI after publication. No full workflow dispatch/rerun, release assets, live GitHub publication fixture, tag or global installation is part of this issue. Keep #12 deferred; this feature does not absorb the log-parity backlog.

## Testing Decisions

Use **one new public seam: a real MCP client communicating over stdio with the built `an mcp` process**. The same scenarios start the Node entry point and a separately compiled native executable. Do not replace the server with an in-memory transport, call private handlers directly, export helpers solely for tests or mock the stack engine. A small persistent client fixture is necessary; reuse the existing CLI launcher and temporary Git fixtures for setup, independent state observation and direct-CLI controls. A protocol-aware SDK client is the normal driver; a raw framing observer may check stdout at that same wire boundary.

Good tests assert actual MCP responses, process exit/liveness, request association and independently observed Git outcomes. Expected branch relationships, commits and files come from the declared fixture/control, not the candidate's own renderer. Snapshot refs, effective HEAD, parents, index, local files and relevant continuation/lock state as appropriate. Successful writes assert their intended changes; refusals/inspections assert preservation within the existing direct CLI contract. Do not equate exit zero, returned text or absent exceptions with a correct operation.

Use these **fifteen named scenarios**, combining related checks within each rather than generating a route/flag/client Cartesian matrix:

| #   | Observable acceptance                                                                                                                                                                                                              |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Start outside Git without credentials; negotiate the two required protocol versions in representative connections, discover exactly the two tool schemas, identify the bundled version, and check root/server help and completion. |
| 2   | Call `learn_an` outside Git; validate its supported English workflow examples and instruction hierarchy without repository/config changes, authentication or automatic execution.                                                  |
| 3   | Read log/info through MCP and compare stdout/stderr/status with the same direct CLI; preserve the fixture and prove self-launch uses this build even with unusable `an`/`ch`/`gt` sentinels on PATH.                               |
| 4   | Create a real branch/commit from staged fixture content with spaces, Unicode and shell-looking message text; verify exact message/identity and absence of an expansion/execution sentinel.                                         |
| 5   | Modify and restack a small real chain through MCP; compare final commits, parent relationships and files with a direct-CLI control while preserving another stack.                                                                 |
| 6   | Send overlapping requests for two repositories, including a linked-worktree cwd; associate each response correctly, preserve the caller, and refuse missing/relative/file/contradictory cwd before command effects.                |
| 7   | Exercise malformed arguments, unknown tool/method and an ordinary CLI failure; distinguish protocol/tool errors, preserve early-refusal state, and successfully execute a later request in the same connection.                    |
| 8   | Use refusal sentinels for prompts/editor/pager, quiet/debug controls and a recursive MCP request; obtain usable errors/data without UI, hangs, recursive servers or protocol stdout contamination.                                 |
| 9   | Refuse one frozen mutation and one branch occupied in another worktree through MCP; retain refs, parent/frozen state, index and dirty linked files.                                                                                |
| 10  | Produce a genuine rebase conflict through MCP, observe partial state, stop the session, resolve fixture files with ordinary tooling, start a new MCP session and successfully continue; compare with direct recovery.              |
| 11  | Submit an explicitly selected fixture stack using a local bare remote and the existing controlled gh adapter; observe push/base/draft/metadata outcome and preserve an unrelated branch. No actual GitHub PR or token is used.     |
| 12  | Deliver a complete large UTF-8 result including its exact final-LF boundary; separately exceed a configured capture limit, report truncation/error explicitly and keep the session usable.                                         |
| 13  | Time out a real CLI call blocked by a controlled external hook/tool with an observable child; stop owned descendants, report the deadline and reached state, preserve a foreign lock/control process, and run a later command.     |
| 14  | Cancel active and queued requests using public notifications; ensure queued work never starts, active work stops, late/unknown cancellation does not affect the next request and no rollback is claimed.                           |
| 15  | Close client stdin/terminate the server while an owned child is active; stop owned descendants/reap the child, discard the queue, preserve unrelated processes and existing recovery data, then reconnect for inspection.          |

Use fixture-owned marker files and bounded waits to observe hook/child readiness and effects; do not assert private process-management call counts or rely on an arbitrary sleep as proof. Short public server timeouts/output limits keep lifecycle cases bounded without a test-only execution seam. Observe at least an ordinary child/grandchild on the host under test; do not infer global process or network containment.

Prior art includes the existing command process launcher, cwd/inspection snapshots, create/reorder/frozen fixtures, parser-failure refusals, non-interactive editor/pager sentinels, genuine conflict continuation and controlled submit/bare-remote adapter. Add only the small MCP client lifecycle support needed to reach the new public interface. Run affected direct CLI registration/help/interaction controls and build, uncached source/test lint and typecheck. Each applicable new scenario executes on both runtimes without silent skips; retain concise per-scenario outcomes and representative protocol/output records with hashes. Existing unaffected engine behavior is covered by its suites, not repeated wholesale through MCP.

The approved boundary excludes real GitHub publication and an application-by-application MCP-client matrix. A single independent SDK client at the real stdio boundary proves the server contract; future installation in the owner's preferred agent is a separate authorized smoke test. The full CI matrix remains off.

## Out of Scope

- Remote HTTP/SSE hosting, ports, OAuth/MCP accounts, a Graphite service backend or a new credential store.
- Automatic client registration, global installation, releases, tags, asset builds or paid full-matrix validation.
- A tool per CLI command, a domain-specific stack JSON API, binary-output/base64 transport, streaming command-output/progress UI, persistent jobs, resumable MCP sessions or background task extensions.
- A new permission/approval service, shell sandbox, capability allowlist, arbitrary executable selector or wholesale Git/SSH/credential-helper policy redesign. User/repository/client authorization still governs the general execution tool.
- Copying Graphite's learning guide, prescriptive tool instructions or unmeasured implementation details; exact byte parity of learning/errors is not required.
- A general parser rewrite, new engine/concurrency model, repository migration, broad lock repair, automatic retries, conflict resolution or transactional rollback.
- Changing log rendering/classic order, multi-trunk behavior or other deferred parity work in #12.
- Global cleanup of arbitrary processes, certification of intentionally detached third-party daemons, Windows process supervision, all-platform certification or an exhaustive agent-client matrix.

## Further Notes

The [research report](../research/mcp-support-2026-10-27.md) and its [evidence manifest](../verification/evidence/mcp-support-spec-2026-10-27/manifest.json) separate direct source facts, shipped Graphite observations, proposed Anthracite behavior and untested areas. Its text-only command-error result is not a requirement to reproduce weak error signalling in Anthracite.

Their lifecycle/error requirements inform the transport; the command envelope, queue, timeout and output limits above are explicit Anthracite product decisions.
