# Scoped feature refresh, cleanup consent and restacking for sync

## Problem Statement

Developers and agents need one predictable operation to synchronize the existing local branches belonging to their configured trunk. In released Anthracite 0.5.1, sync updates trunk and PR information but does not refresh feature heads. Automatic restacking is disabled by default. Automating merged/closed branch cleanup currently requires force, which also grants permission to reset trunk to its remote version. Cleanup consent and history replacement are different permissions.

The bounded comparison of Graphite 1.8.6 with Anthracite 0.5.0 demonstrates feature-head refresh during sync, Graphite's default restacking, and cleanup-only consent that does not authorize a divergent trunk reset. It does not prove every sync scope, conflict or service combination. The historical B02 cleanup traversal defect is already repaired in 0.5.1.

The implementation baseline is merged main `26c8b64373e0c57bf2fd833a6a65bfeb827d8bfd`, including PR #77's graph-aware get implementation. Its shared update machinery provides pinned sources, guarded application and owned continuation. Sync must reuse those boundaries with its own selection, trunk-reset, cleanup and checkout policies. This specification is intended Anthracite behavior, not certification of complete Graphite parity or functionality already released on npm.

## Solution

Make sync refresh eligible existing tracked feature branches belonging to the single configured trunk, then perform separately authorized cleanup and default local restacking. The selection is repository-wide within that trunk, independent of the current feature checkout. It does not import missing branches or discover remote-only successors.

Plan incoming changes, cleanup choices and necessary survivor maintenance before changing local heads. Apply selected incoming updates before cleanup and replay, preserving explicit graph parents. Refresh existing open-PR feature sources; preserve unpublished local-only work and retain closed/merged branches when cleanup is declined or blocked. Closed/merged associations inform cleanup rather than forcing a fetch of a remote head that may already have been deleted.

Add cleanup-only `--delete-all`. Preserve the existing explicit sync force authority for cleanup and trunk reset, but do not infer feature overwrite permission from force. Enable restacking by default with `--no-restack` to defer local replay. Retain the original checkout when it survives; if approved cleanup deletes that branch, finish on configured trunk. Real conflicts retain a bounded sync-owned workflow for fresh `an continue`/`cont`.

For example, when main advances and an open child has a newer remote head, sync refreshes that head before maintaining its local descendants. If the child's former parent PR has merged, accepted cleanup removes only eligible local branches, preserves surviving PR identities and reparents/restacks survivors. `--delete-all` alone cannot reset a divergent main or overwrite a divergent child.

## Implementation Decisions

1. **Baseline, selection and routes.** Extend the existing sync routes, including top-level sync and legacy repo sync/repo s, using the single configured trunk/repository/remote. Select every currently tracked feature belonging to that trunk, regardless of physical checkout, including independent root stacks. Sync has no branch target or get/downstack selector in this delivery. Reject cycles, inconsistent associations and required untraceable parents before local application. Do not import missing parents, discover remote-only descendants or treat an untracked branch as implicitly selected. A repository with no tracked features can still perform its permitted trunk phase.

2. **Interface and deliberate defaults.** Keep pull/-p and delete/-d true, force/-f false, and existing progress and restack/-r forms. Change restack to true; support ordinary explicit boolean/negative forms consistently across routes. Add delete-all default false with normal boolean semantics, without another short flag. No-delete suppresses cleanup even with delete-all or force. No-pull suppresses trunk fetching/application only; it does not suppress PR information lookup or feature-head refresh. No-restack suppresses automatic local replay, not incoming updates, accepted cleanup metadata changes or an explicitly selected divergence-reconciliation rebase. Do not add a feature-refresh switch or persistent preference in this round. Document these distinctions and the absence of a flag recipe that reproduces the former trunk/PR-info-only operation; get with explicit scope remains available when repository-wide sync is unwanted.

3. **Fresh identities and refresh eligibility.** When repository GitHub integration is enabled, read PR state and identity from configured GitHub. Prefer a stored PR number and verify the exact head name/repository; unassociated tracked branches may acquire a verified open-PR association under existing rules. Normal absence without an association is local-only work, not an error or publication request. Missing associated PRs, auth/transport/rate-limit errors, malformed responses and identity changes are failures. Eligible open PR heads are refresh sources. Fresh closed/merged associations are cleanup inputs and are excluded from feature-head refresh even when cleanup is declined, disabled or blocked; name that retained branch and its reason. A missing remote head for an open associated PR fails; a deleted remote head for a known closed/merged cleanup candidate is not required. Preserve existing local merge/empty-branch cleanup eligibility, including protection of an empty unassociated branch. When GitHub integration is explicitly disabled, make no GitHub calls or new PR-derived feature selections; retain the existing trunk/local cleanup/restack flow, disclose skipped PR/feature refresh and never describe cached PR statuses as freshly verified. Do not silently enable integration or demand a login for that local mode.

4. **One bounded plan, separate phases.** Snapshot the existing graph, physical checkout, relevant local heads/metadata, required open-feature sources and optional remote trunk. Derive valid PR-parent transitions, reconciliation decisions, cleanup selection/effective survivor parents and prospective maintenance before local head changes. Collect required terminal choices before application; cancelled choices abandon that plan. Remote lookup/fetch/cache/PR-info metadata and owned pin writes may occur while discovering blockers: this is not a write-free transaction. Apply trunk, then all incoming feature updates parent-first, then approved local cleanup, then local maintenance, then final checkout and guarded owned-state cleanup. Never replay a descendant before its selected remote update and mistake the resulting local head for divergence. Keep per-node source and parent identities; an array's previous sibling is never its parent.

5. **Trunk authority remains sync-specific.** With pull enabled, identical/fast-forward trunk updates use guarded existing behavior. Local-ahead or divergent trunk may reset only under the existing explicit sync force authority or affirmative terminal reset choice collected before application; otherwise refuse and preserve its commits. Delete-all alone supplies neither reset nor feature-overwrite permission. No-pull means no trunk fetch/reset, including with force. A permitted reset remains subject to local work, worktree and hook protections. Do not weaken get's FF-only trunk contract or transfer sync reset authority into it. Explain the deliberate compatibility difference from get and the narrower measured Graphite delete-all case.

6. **Feature updates and reconciliation.** Apply identical or fast-forward feature sources without force; adopt a validated new existing parent when the source permits the transition. A parent selected for later cleanup stays available through incoming application; effective cleanup reparenting then follows the separately approved survivor plan. Preserve local-only feature commits on noninteractive divergence by refusing before planned head changes. Reuse existing explicit terminal rebase/overwrite/abort choices for eligible divergent selected features, collected before application. Frozen features cannot choose local rebase. Sync force retains its previous cleanup/trunk meaning and never silently authorizes feature overwrite. Neither delete-all, restack nor a cached choice authorizes an unplanned source, new branch or changed overwrite decision.

7. **Cleanup-only consent and eligibility.** Delete-all bypasses per-candidate confirmation only for the existing safe-to-delete selection; force retains its existing cleanup consent separately from its trunk permission. Without either flag, noninteractive cleanup declines candidates and terminal cleanup asks under existing interaction policy. Declined candidates remain; they do not stop searching their descendants. Keep B02's traversal below open/declined ancestors, combined planning of separated candidates, deduplication and dependency order. Preserve existing frozen-target deletion rules while excluding a group whose mandatory surviving branch cannot be safely reparented/replayed. Explain excluded groups and pending maintenance rather than claiming they were cleaned. Delete-all cannot bypass survivor, file, active-operation or worktree protection, delete arbitrary branches, remove remote refs or edit PRs.

8. **Cleanup and incoming graph interaction.** Open survivors receive their selected incoming updates before local deletion/reparenting. A fresh PR base may already name trunk or another retained parent; otherwise an approved local cleanup can reparent survivors through a removed closed/merged ancestor under the existing cleanup contract. Derive this effective local parent explicitly, without editing the remote PR base or treating the remote base as permission to resurrect a deleted branch. Removing an ancestor never changes an unrelated retained sibling's PR identity or unique work. If cleanup was declined/excluded, retain that ancestor as an anchor and report any resulting deferred or protected work. A required frozen survivor still blocks its cleanup group with no-restack: disabling replay is not permission for a forbidden parent change.

9. **Maintenance scope and content.** With restack enabled, maintain branches in the selected single-trunk graph that need repair against their resulting parents, including local-only descendants, cleanup survivors and independent root stacks affected by trunk advancement/reset. Unlike target-bounded get, repository-wide sync may legitimately maintain multiple independent stacks. Parent/source changes and already-stale local bases inform the explicit maintenance selection; do not rewrite an already-valid branch gratuitously. Preserve each surviving branch's own commits, authors, full messages and resulting file changes, dropping already-applied patches through ordinary Git behavior. Disclose this selection separately from remote refresh and deletion. With no-restack, preserve affected feature heads after incoming updates, make only approved cleanup/metadata changes and identify pending repair. Existing generic frozen-anchor skip behavior remains distinct from mandatory survivor refusal.

10. **Frozen inbound work and local-only anchors.** Existing frozen branches may receive permitted inbound identical/FF or explicitly selected overwrite updates while retaining frozen status. Never unfreeze them. Do not locally replay frozen history; retain its tip as an anchor where existing policy permits editable descendants. Name unreplayed/skipped work. A freeze introduced after planning cannot be overwritten by stale metadata; unfreezing cannot silently expand the saved plan's rewrite authority. Local-only branches remain unpublished, retain their head/content unless authorized maintenance replays their own commits, and cannot be replaced by a convenient remote branch. No new import-ownership decisions are needed because sync imports nothing.

11. **Known and late protection.** Preserve conservative tracked-dirt refusal and untracked/ignored collision checks. Preflight physically affected trunk/features, cleanup targets, mandatory survivors, replays and final checkout; unrelated occupied branches that need no writes are not blockers. Never modify another worktree. Refuse known invalid plans before affected local head/parent/deletion writes, subject to explicitly allowed frozen cleanup exclusions. Recheck relevant local heads, metadata/parents, freeze status, physical checkout and worktree occupancy immediately around writes and hook-sensitive publication. Prevent Git's rebase updateRefs configuration from rewriting out-of-scope refs during owned replays without altering user configuration. Keep original hooks enabled. Report reached partial effects rather than forcing stale publication, rolling back another actor or expanding consent.

12. **Final checkout and completion invariant.** Capture physical original branch or detached OID before application, without using a continuation override. On full success restore the surviving original branch at its authorized current head, or the exact detached OID. When and only when this operation's accepted cleanup actually removes the original branch, use configured trunk as the declared fallback and report it. An unexpectedly disappeared ref is a failure, not permission to recreate it or silently fall back. Preserve collisions/occupancy checks for final switching. Verify expected surviving heads, parent/PR metadata, authorized deletions and intended physical checkout after final hooks and again after hook-sensitive source-ref cleanup, before discarding owned recovery. Permit existing freeze-only deltas without accepting concurrent topology/head changes. A final mismatch is nonzero, preserves actual concurrent state and reached work, and retains appropriate manual guidance. Do not reintroduce the final-completion defect fixed during #77 review.

13. **Owned conflict continuation.** Reuse ordinary Git rebase and continue/cont through an optional sync-owned record with explicit operation kind, repository/common-dir/worktree identity, pinned source/parent graph, exact refresh/cleanup/maintenance selections, prior consent and remaining phases, progress and final-checkout/fallback policy. Keep source objects reachable during a valid owned workflow. Bind the complete envelope and legacy mirrors to the active rebase ownership marker; distinguish it from get, landing and legacy queues. Resume a verified real reconciliation or maintenance conflict from a fresh process, preserving each remaining node's parent and the saved policy rather than rereading defaults. Before continue-all stages anything or advances Git, revalidate ownership, active and remaining participants, sources, heads/parents and protections. Retain freeze-only status changes under existing rules. Completing continuation performs the same guarded completion path as initial execution.

14. **Pending cleanup after a pause.** Continuation may complete cleanup already authorized in the saved plan; it cannot discover additional candidates, ask new deletion questions or inherit later flags. If reconciliation paused before cleanup, freshly verify the original pending candidates' PR identities/states before their deletion. A material status/identity change, such as a closed PR reopening, requires refusal/replanning rather than deleting from stale classification; lookup failure is not consent. Do not rerun unrelated discovery or fetch new source heads while resuming. If PR-dependent pending cleanup needs fresh verification but integration has since been disabled, refuse that advancement with inspection guidance instead of bypassing the setting or claiming cached state is fresh; local-eligibility-only cleanup needs no PR lookup. Completed deletions remain completed. Disclose that a pending-cleanup resume can require GitHub read access; it is not promised fully offline. Preserve the reached state and manual boundary if a completed rebase cannot safely advance into its next phase.

15. **Failure, abort and uncertain effects.** Return zero only after all declared phases complete, including explained policy skips and explicitly deferred maintenance. Nonzero diagnostics identify confirmed trunk/feature updates, parent changes, deletions/replays, failed/active phase, pending work and actual checkout. Keep essential diagnostics under quiet/noninteraction. A real conflict retains Git state and instructions from the original project directory. Raw Git abort cancels only its active rebase; it does not undo earlier trunk resets, incoming updates, cleanup or completed rewrites. Stale, foreign, changed, raw-aborted, missing or incompatible intent cannot consume another recovery file, stage blindly or execute an unverified queue. Non-conflict interruption or uncertain completed publication has guarded inspection/manual recovery, not a general automatic retry/rollback promise. Cleanup may already have removed some source refs: describe them neutrally for inspection rather than claiming every pin remains.

16. **Compatibility of shared boundaries.** Generalize/reuse the existing graph-aware snapshot/application, replay, protections and ownership checks with explicit sync selections and authority. Do not implement sync by repeatedly invoking public get with inherited defaults, introduce a parallel stack engine or build a generic transaction system. Get remains target-bounded, FF-only for trunk and cleanup-free. Its existing saved workflows, other structural/landing operations and legacy sync continuations without new intent stay readable and follow their original contract. Add only optional owned state; finish a new pending sync workflow before downgrading. Cancellation/MCP timeout use existing process supervision without claiming atomic cancellation or remote rollback.

17. **Public guidance and automation.** Update command reference, compatibility/release guidance, help/completion and existing MCP learning together. State repository-wide existing-branch refresh, default replay, no-pull's trunk-only meaning, no-delete precedence, narrow delete-all authority and legacy force's separate reset power. Explain changed automation behavior and the absence of an exact old-default recipe. Existing tests intentionally expecting no replay become explicit no-restack compatibility cases; old assertions that sync never refreshes feature heads must be replaced with preserved-scope/new-default evidence, not left misleading. Effective noninteraction launches no prompts, editors, browsers or pagers. Existing MCP tools/literal cwd/argument delivery and publication approvals remain unchanged. Sync itself performs no GitHub writes or pushes.

18. **Delivery boundary.** This delivery publishes an English specification and source/evidence record only, using ready-for-agent triage. Implementation, ticket decomposition and an implementation PR require their later workflow. Future implementation acceptance uses the approved public seam and bounded Node/native/npm checks below, with CI/full matrix off unless the owner explicitly changes that constraint. Do not change executable code, dependencies, workflow configuration, release versions, owner installation or live GitHub fixtures in specification delivery. Retain historical evidence/version boundaries and distinguish proposed default behavior from measured Graphite behavior.

## Out of Scope

- Multiple trunks, sync all-trunk selection, alternate providers/remotes and new repository configuration.
- Remote-only discovery, importing untracked/missing branches, Graphite indexing/accounts and hosted-service emulation.
- Get cleanup or changed get defaults/force authority; a new feature-refresh selector, new sync branch selector or persistent cleanup preference.
- Pushes, PR creation/base edits, review/role changes, remote branch deletion, submit or land inside sync.
- Arbitrary local resets/unfreezing, implicit feature overwrite through sync force, worktree bypass and broader dirty-worktree tolerance/stashing.
- A generic undo/abort/rollback engine, multi-ref transaction, global continuation migration or automatic recovery of every interrupted write.
- New MCP tools, authentication methods, test framework/dependencies, exhaustive platform/shell/supervision tests or unrelated maintenance such as B01.
- Implementation/tickets/PRs, release assets, npm publication, owner installation changes, live fixtures, CI or the full matrix in this specification delivery.
