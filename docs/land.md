# Scoped landing

`an land [branch] --dry-run` explains the unique tracked chain from trunk through the selected local branch. The default is the physically checked-out branch. Numeric branch names remain literal branch names. Landing requires an initialized repository and attached checkout. Raw `an merge` remains Git merge passthrough.

Since 0.6.3, fresh plans put blockers first, followed by the ordered PR scope, requirements, separately named survivor maintenance and confirmed-merge cleanup. Section icons distinguish blockers, merge order, maintenance and cleanup. Blocked plans label the remaining scope as conditional. Dirty-worktree blockers suggest `git status --short`. Add the existing `--debug` option for exact commit IDs, replay boundaries, PR URLs and low-level readiness details. The candidate after 0.6.3 applies the same compact layout to resumed landings, including normal application before confirmation. Recovery phases, captured/reached heads and replay boundaries are available with `--debug`. See the [bounded comparison and presentation verification](verification/land-presentation-2026-11-02.md) and [resumed-landing verification](verification/land-resume-presentation-2026-11-02.md).

The preview lists merge order, repository/PR/head/base identities, fast-forward trunk advancement, each mandatory surviving descendant and fanout replay, pre-existing remote-head and PR-base/dependency-footer updates, and landed-only cleanup. Disclosed maintenance uses a dependency-first traversal, ordering each parent's children by branch name so previews and replay order are stable across runtimes and retries. An unpublished survivor stays unpublished. Independent trunk stacks are outside the scope.

**Deferred publication (source candidate after 0.6.15):** new landings retain immediate local replay, including early conflict detection, but publish a later merge target only when preparing its own merge. After each confirmed merge, the next target's latest reached head is pushed under its captured lease and its existing PR base/managed footer is verified before deleting its landed parent. More distant targets defer both the push and PR reconciliation. Their remote heads, PR bases and dependency footers can temporarily lag the reached local stack; this is disclosed pending work, not confirmed publication or fresh readiness. The plan reports readiness for the next merge only. Each later target receives fresh head, policy, approval, required-check and publisher verification after publication. Published non-target survivors retain eager maintenance; local-only branches remain unpublished. A sibling maintained after its affected ancestor merges is not newly promised another replay onto final trunk.

New operations persist version-2 landing records. Existing version-1 records retain their original eager publication order, including partially completed maintenance, without conversion. Both versions use the current required-check policy. Finish a pending version-2 landing before downgrading to an older CLI that cannot read it. An interruption preserves reached local work, last verified publication identities and pending push/base/footer obligations. Inspect the saved plan, resolve an owned conflict locally with `an continue` when appropriate, then explicitly resume `an land [original-target] --yes`. Recognized acknowledged pushes and matching PR updates are read back before further effects; deleting recovery or resetting refs is not a supported shortcut.

Pending recovery previews show all remaining merges, mandatory replay/push/PR updates, landed-only cleanup and the expected final checkout. A branch also selected for a later merge is explicitly labelled; other surviving branches stay outside the merge set. Fresh blockers precede a conditional scope, and exact reached phase/head identities remain in debug output. They check fresh local/remote identity and readiness through the same adapters, including after the original target was deleted. Dirty state, unresolved replay, changed leases and pending or unknown readiness return nonzero. A reached local head not yet pushed cannot borrow readiness from its older published head. Deliberately deferred later targets do not block the verified next target solely because their new heads are unpublished; their independent draft/review blockers still apply.

Resuming with `land` performs that same preserving inspection and prints the same freshly checked plan before confirmation, including with `--yes`. A dry-run stops after the report; application may proceed only after confirmation through the existing phase-specific guards. Known running required checks can enter bounded waiting, and saved mandatory maintenance can finish before fresh readiness is established. Inspection findings never authorize a merge or bypass protection; execution revalidates before effects, including changes made after the report was printed.

Preview uses the preserving inspection path. It writes no repository refs, index/files, metadata/cache, recovery, remote refs or PRs and launches no browser/editor/pager. When remote objects are absent, ancestry is inspected in a disposable bare repository outside the working repository.

Preflight checks clean tracked and ordinary untracked work, Git/recovery operations, frozen participants, other worktrees, local/published head equality, trunk fast-forward compatibility, matching PR identities and initial parent bases. It discovers all active rules pages and classic protection evidence, then checks direct rebase availability, queue/unsupported policy, required reviews/checks, known failing/pending checks and GitHub mergeability/readiness. Empty checks or reviews alone grant no permission. A successful unprotected-branch response plus complete applicable rules establishes absence; a classic-protection 404 alone never establishes absence. Verified already-merged members of the selected chain appear as cleanup-only after fresh head/merge-result reachability checks. They retain their original local and remote heads until leased cleanup, receive only necessary local metadata reparenting, and are never replayed, pushed or edited as surviving PRs. Their actual surviving descendants still receive mandatory maintenance.

Since 0.6.2, when active rulesets explain protected status and the classic endpoint returns the structured `Branch not protected` 404, Anthracite makes a separate read-only GraphQL query. It requires the exact repository and branch, administrator visibility, an explicit null `branchProtectionRule` and no GraphQL errors before proceeding with all ruleset requirements. Generic 404s, 403s, missing access, partial responses and contradictory identities remain blocking. A present classic policy is still combined with rulesets using the stricter review count and the union of checks/publishers; the repair does not change merge authority. See the [focused verification](verification/land-ruleset-only-policy-2026-11-02.md).

Check runs count as successful only when `status` is `COMPLETED` and the conclusion is `SUCCESS`, `NEUTRAL` or `SKIPPED`; missing/nonterminal status takes precedence over an old success conclusion. Commit status contexts use their own `state`. Classic protection must return the exact canonical URL for the verified repository name and encoded trunk; foreign hosts/paths, credentials, suffixes, query strings and fragments refuse.

Fixed-publisher requirements trigger additional read-only Check Runs requests for the exact PR head. Every page must be retrieved completely with stable counts and unique run IDs. Each required name/app-ID pair needs one matching run with that head, `completed` status and an accepted terminal conclusion; mismatched, stale, ambiguous, missing or unavailable publisher evidence blocks landing. Legacy commit statuses cannot establish a required app identity. The same asynchronous verification runs during preflight and immediately before every merge, including after replay.

GitHub documents [classic app identity](https://docs.github.com/en/rest/branches/branch-protection#update-status-check-protection) and [ruleset integration identity](https://docs.github.com/en/rest/orgs/rules#create-an-organization-repository-ruleset) as separate requirements. Its [CLEAN definition](https://docs.github.com/en/graphql/reference/pulls#mergestatestatus) describes mergeability and passing commit status; it does not explicitly establish publisher provenance in this rollup. Anthracite therefore verifies the [Check Runs response](https://docs.github.com/en/rest/checks/runs#list-check-runs-for-a-git-reference), including app identity and head SHA, rather than treating a matching name or `CLEAN` alone as provenance. Classic `app_id: -1` explicitly allows any app and needs no extra publisher lookup. These are adapter-tested checks, not live-service certification.

`an land [branch]` prints the plan and asks for terminal confirmation. Noninteractive or quiet application requires `--yes`. Cancellation happens before writes; confirmation is followed by fresh local/remote/policy revalidation. The selected chain lands bottom-up. Necessary surviving descendants, including sibling arms and branches above the target, receive maintenance without becoming merge targets. `--yes` does not bypass blockers. No count, PR-number/URL, wildcard/all-stack, force/admin/queue or alternate merge-method route is provided.

Application records owned intent before its expected-head direct rebase merge. It confirms the merged PR identity and actual remote trunk ancestry, fast-forwards local trunk, reparents every affected direct root before replay, then replays survivors in dependency order using their captured old boundaries. Only pre-existing remote heads push, with explicit captured-OID leases. Existing PR identities, user titles/body, roles and draft states survive base/managed-footer updates; missing PRs and unpublished heads stay that way. Each next selected merge requires fresh head/base/policy/check/review readiness after all necessary maintenance. Completed independent arms are not replayed, republished or required to become editable again for later merges.

The post-0.6.2 candidate waits within the same confirmed application or resumption when the next PR has known queued/running required checks. It polls every five seconds, with a default check-wait limit of 600 seconds per PR. `--wait-timeout <seconds>` accepts whole seconds from 0 to 86400; 0 retains immediate-stop behavior. Each poll rechecks local state, repository identity, exact PR head/base and remote lease, trunk ancestry, policy, approvals and check evidence. A wait never repeats a merge request or starts maintenance. Only fully verified readiness permits the next merge. `UNSTABLE` can reflect optional failures and is not an independent blocker; `BLOCKED` can enter waiting only with concrete pending required checks. Unknown readiness, conflicts, failed required checks, missing approvals, missing required checks/publishers and unavailable evidence still stop progress.

**Required versus optional checks (candidate after 0.6.15):** only checks required by freshly verified classic protection or applicable rulesets block merging or enter the wait loop. Optional running, failed or cancelled checks are shown as nonblocking warnings in fresh plans, saved previews and execution. This applies equally to check runs and commit statuses; workflow names such as `publish-beta` or Pages have no special exemption. If an optional workflow must gate merges, configure it as required in GitHub. A verified empty requirements list is different from unavailable policy evidence, which remains blocking. GitHub still enforces the merge request; Anthracite does not request an administrative bypass. Published 0.6.15 and earlier retain the previous all-checks behavior.

Dry-runs and initial preflight return immediately with current blockers; they do not wait or authorize application. The wait is for pending checks discovered after confirmation, including checks triggered by Anthracite's own pushes and pending checks in an existing landing record. A timeout returns nonzero, names the next PR and says that no merge request was sent for it. Completed work and the operation's existing recovery version are retained. Ctrl-C/SIGTERM preserve progress and release the owned lock. Inspect a fresh dry-run before explicit resumption. Existing client/MCP deadlines can interrupt sooner than the check-wait limit; they neither roll back earlier work nor authorize automatic resumption.

Landing requires one identical resolved fetch/push transport and a declared remote naming the configured github.com owner/repository. Supported declarations are `https://github.com/owner/repo[.git]`, `git@github.com:owner/repo[.git]` and `ssh://git@github.com/owner/repo[.git]`, without credentials in HTTPS URLs, custom ports, query strings or fragments. Endpoint hashes and declared identity are rechecked before effects and after ordinary hooks. Git `insteadOf` rules and SSH routing remain trusted user transport configuration; this validates the declared repository and stable resolved transport, not the actual server reached through that routing.

Cleanup deletes only the unchanged published landed feature ref with its explicit lease, and atomically removes the landed local head and metadata. Ordinary hooks run. Competing heads, failed hooks, authentication expiry and rejected writes stop later work and retain earlier confirmed effects. The original checkout is restored when it survives; otherwise trunk is selected. Pushes, PR edits and merges are separate service effects; the workflow promises neither rollback nor exactly-once remote execution.

An incomplete run returns nonzero and keeps `.anthracite_landing` in the Git common directory. Inspect with `git status`, `an pr <branch>` and `an land [original-target] --dry-run` in the printed original worktree. Apply `an land [original-target] --yes` only after inspecting reached work. The saved original target works after its branch was deleted; an implicit target resumes that same identity. A lost merge response is reconciled read-only; an uncertain unconfirmed merge is never automatically repeated. A definite authentication/permission HTTP rejection permits only a later explicit run after its structured error and gh status agree and a fresh exact PR read confirms it is still open and unmerged. Reauthenticate through ordinary tooling before that explicit resumption. If readback is unavailable, malformed or disagrees, uncertainty remains guarded. Already pushed reached heads and already correct PR bases/footers are read back before further effects. Invalid/foreign records, another target/repository, changed scope, changed participants or lease races cause preserving refusal. Ordinary mutation commands refuse while landing is pending; inspection and explicit freeze/unfreeze remain available.

The candidate after 0.6.4 also permits an independent merge to advance remote trunk during a saved landing. The PR's base commit snapshot need not equal the live trunk tip: both that snapshot and local trunk must be verified ancestors of current remote trunk. Preview and execution apply this same ancestry guard without fetching into the project or requiring a separate sync. Unknown or unrelated base snapshots and non-fast-forward trunk history refuse before another merge request. All fresh head, policy, review, check and lease guards still apply; local trunk advances only after a confirmed merge.

A genuine replay conflict preserves completed merges/reparents and the landing-owned `.gtcontinue`. If a hook introduces foreign continuation before first publication or replaces the owned file during replay, landing preserves those exact bytes and the active/reached Git state, records reached work where observed, and returns nonzero before overwriting or deleting that file. Such a mismatch requires deliberate inspection rather than automatic continuation. Resolve files deliberately, stage the resolution and run `an continue` in the printed original worktree. Landing continuation is local-only: it never merges PRs, pushes heads or edits PRs. Fresh guards protect every remaining mandatory participant before staging or starting the next replay. The landing record remains for explicit `an land [original-target] --yes` remote resumption. If a completed replay encounters a later frozen/occupied participant or a rejected pre-rebase hook, the exact durable pending queue can resume with `an continue` after the blocker is resolved. Public freeze/unfreeze preserves the saved identities and changes only protection metadata; it does not authorize new participants or remote work.

Raw `git rebase --abort` (or `an rebase --abort`) cancels only its active Git rebase. It does not undo merges, parent updates, completed replays or publication. If no owned active rebase or proven pending queue remains, both records and reached refs are preserved. Inspect `git status`, `git log --oneline --all --decorate` and `git show refs/branch-metadata/<branch>` alongside the saved record in the original project. A crash between a ref/metadata update and durable confirmation, or an incomplete metadata publication, can require deliberate manual reconciliation. Do not delete recovery, reset branches or retry patches to make validation pass; absence of a rebase and ancestry alone do not prove completion.

SIGINT/SIGTERM retain progress and release only the current process's lock. Explicit application/resumption may reclaim a cache lock only when its exact PID/timestamp acquisition matches the validated landing record, the PID is demonstrably absent and the bytes remain unchanged immediately before removal. PID reuse, live/foreign/invalid locks and old records without acquisition proof refuse. A crash after lock acquisition but before the first record has no ownership proof and requires manual inspection; no remote effect starts before durable merge intent. Unrelated Git locks remain untouched. MCP cancellation/timeouts use the existing owned process-group supervision and retain the same recovery limits.

These are controlled-adapter workflows for same-repository github.com PRs. They do not claim live GitHub acceptance or enterprise compatibility. Missing classic-protection access and incomplete publisher provenance remain unknown/blocking; empty review/check arrays alone establish neither absence of policy nor readiness. B01's legacy `an test` scope flags remain broken and were not used to bound this acceptance.

The source candidate after npm 0.6.6 supports a narrowly verified private-plan route when the configured trunk's first applicable-rules REST page fails with the exact structured message “Upgrade to GitHub Pro or make this repository public to enable this feature.” The JSON body must carry status `403` and the canonical branch-rules documentation URL, and the failed gh process must return exit code 1 with the matching HTTP 403 diagnostic. Generic 401/403/404 responses, rate limits, network errors, malformed or contradictory responses, other endpoints and later-page failures remain blocking. This is implemented source-candidate behavior, not a claim about the published 0.6.6 package. See the [implementation and delivery verification](verification/land-private-plan-policy-implementation-2026-11-03.md), [approved specification](specs/land-private-plan-policy.md) and [historical read-only observations](verification/land-private-plan-policy-spec-2026-11-03.md).

The normal REST repository and branch reads must first verify the configured private repository, administrator access, the exact trunk and `protected: false`. A separate administrator-visible GraphQL read must independently match that private repository and trunk, explicitly return null classic protection, and completely enumerate unfiltered repository and inherited rulesets using `includeParents: true`. Every page must agree on identity and total count; IDs must be unique, cursors must advance and a terminal page must account for the whole inventory. Traversal is bounded to 100 pages of at most 100 nodes. An empty inventory or an inventory containing only explicit `DISABLED` enforcement is accepted. Any active, evaluate, unknown or missing state refuses this narrow proof, regardless of target or apparent branch applicability. Evaluate mode is outside the supported proof set; it is not described as active enforcement. Missing fields, errors, inaccessible pages, contradictory classic protection or incomplete inventory preserve refusal.

A successful plan says `Policy: Independently verified despite plan-restricted REST access.` This proves only the bounded policy inspection. PR readiness still requires fresh identities, leases, mergeability, reviews, checks and any publisher provenance. Rebase availability, confirmation, direct rebase merges, survivor maintenance, leased publication and landed-only cleanup keep their existing contracts. Ordinary REST inspection remains preferred whenever available and applies its current full requirements.

Each initial inspection, saved preview/resumption, per-merge guard and check-wait poll obtains fresh policy evidence. Recovery stores no durable exemption. If evidence changes or becomes unavailable, the next merge is refused; completed merges and reached maintenance remain recorded. Confirmed resumption can finish already-owned mandatory maintenance under its existing guards before refusing the next merge. Inspect `git status`, `an pr <branch>` and `an land [original-target] --dry-run` in the original worktree, resolve the reported evidence problem, then explicitly resume under the existing authorization. A recognized subscription restriction does not call for another login, an upgrade, a visibility change or disabling rules. The existing MCP command tool exposes the same behavior with explicit cwd and separate command output/process status; no registration change is needed.

These checks use controlled gh responses with real temporary Git repositories and bare remotes. They do not establish readiness of any real private PR or live GitHub landing acceptance. Separate API reads and merge requests are not atomic; existing fresh guards and GitHub enforcement remain authoritative.
