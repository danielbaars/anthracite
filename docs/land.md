# Scoped landing

`an land [branch] --dry-run` explains the unique tracked chain from trunk through the selected local branch. The default is the physically checked-out branch. Numeric branch names remain literal branch names. Landing requires an initialized repository and attached checkout. Raw `an merge` remains Git merge passthrough.

The preview lists merge order, repository/PR/head/base identities, fast-forward trunk advancement, each mandatory surviving descendant and fanout replay, pre-existing remote-head and PR-base/dependency-footer updates, and landed-only cleanup. Disclosed maintenance uses a dependency-first traversal, ordering each parent's children by branch name so previews and replay order are stable across runtimes and retries. An unpublished survivor stays unpublished. Independent trunk stacks are outside the scope.

Preview uses the preserving inspection path. It writes no repository refs, index/files, metadata/cache, recovery, remote refs or PRs and launches no browser/editor/pager. When remote objects are absent, ancestry is inspected in a disposable bare repository outside the working repository.

Preflight checks clean tracked and ordinary untracked work, Git/recovery operations, frozen participants, other worktrees, local/published head equality, trunk fast-forward compatibility, matching PR identities and initial parent bases. It discovers all active rules pages and classic protection evidence, then checks direct rebase availability, queue/unsupported policy, required reviews/checks, known failing/pending checks and GitHub mergeability/readiness. Empty checks or reviews alone grant no permission. A successful unprotected-branch response plus complete applicable rules establishes absence; a classic-protection 404 remains unavailable rather than proving no requirements. Ruleset-protected repositories whose classic protection cannot be read are conservatively blocked. Verified already-merged members of the selected chain appear as cleanup-only after head/merge-result reachability checks.

Check runs count as successful only when `status` is `COMPLETED` and the conclusion is `SUCCESS`, `NEUTRAL` or `SKIPPED`; missing/nonterminal status takes precedence over an old success conclusion. Commit status contexts use their own `state`. Classic protection must return the exact canonical URL for the verified repository name and encoded trunk; foreign hosts/paths, credentials, suffixes, query strings and fragments refuse.

Fixed-publisher requirements trigger additional read-only Check Runs requests for the exact PR head. Every page must be retrieved completely with stable counts and unique run IDs. Each required name/app-ID pair needs one matching run with that head, `completed` status and an accepted terminal conclusion; mismatched, stale, ambiguous, missing or unavailable publisher evidence blocks landing. Legacy commit statuses cannot establish a required app identity. The same asynchronous verification runs during preflight and immediately before every merge, including after replay.

GitHub documents [classic app identity](https://docs.github.com/en/rest/branches/branch-protection#update-status-check-protection) and [ruleset integration identity](https://docs.github.com/en/rest/orgs/rules#create-an-organization-repository-ruleset) as separate requirements. Its [CLEAN definition](https://docs.github.com/en/graphql/reference/pulls#mergestatestatus) describes mergeability and passing commit status; it does not explicitly establish publisher provenance in this rollup. Anthracite therefore verifies the [Check Runs response](https://docs.github.com/en/rest/checks/runs#list-check-runs-for-a-git-reference), including app identity and head SHA, rather than treating a matching name or `CLEAN` alone as provenance. Classic `app_id: -1` explicitly allows any app and needs no extra publisher lookup. These are adapter-tested checks, not live-service certification.

`an land [branch]` prints the plan and asks for terminal confirmation. Noninteractive or quiet application requires `--yes`. Cancellation happens before writes; confirmation is followed by fresh local/remote/policy revalidation. A single ready leaf based on trunk can be applied. Chains, descendants and fanout execution currently refuse before writes; their complete scope remains available in preview. `--yes` does not bypass blockers. No count, PR-number/URL, wildcard/all-stack, force/admin/queue or alternate merge-method route is provided.

Leaf application records owned intent before its expected-head direct rebase merge. It confirms the merged PR identity and actual remote trunk ancestry, fast-forwards local trunk, deletes only the unchanged published feature ref with an explicit captured-OID lease, and atomically removes the landed local head and Anthracite metadata. Ordinary Git hooks run. A competing head or failed hook stops cleanup and retains confirmed earlier effects. The original checkout is restored when it survives; otherwise trunk is selected.

An incomplete run returns nonzero and keeps `.anthracite_landing` in the Git common directory. Run `an land [original-target] --yes` from the printed original worktree to reconcile and finish, including after the target was deleted. An implicit target resumes that owned saved identity. A lost merge response is reconciled read-only; the merge request is never blindly repeated. Invalid/foreign records, another target, changed local participants or remote refs cause preserving refusal. Unrelated `.gtcontinue` recovery is preserved. Ordinary mutation commands refuse while landing is pending; read-only inspection remains available. `an continue` has no leaf replay to finish and does not merge or publish.

SIGINT/SIGTERM retain progress and release only the current process's lock. A hard kill may retain the existing PID lock and requires inspection; automatic stale-lock reclamation is not implemented. This adapter-tested leaf workflow does not claim live GitHub or enterprise compatibility.
