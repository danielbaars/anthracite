# Landing push deferral: source constraints

Source baseline: merged main [`a3c9f7055c7a42dfe38daee8fb843f21e1763474`](https://github.com/danielbaars/anthracite/tree/a3c9f7055c7a42dfe38daee8fb843f21e1763474), 9 November 2026. This note is source analysis, not a modified implementation or proof that deferred publication is already safe. Synthetic measurements are recorded separately. No production code, user project, live GitHub fixture or CI is changed here.

## Why repeated publication occurs

The landing loop merges one selected PR, advances local trunk, maintains every affected survivor, deletes the landed remote/local branch, and only then advances the merge index. Its survivor set includes later merge targets and captured maintenance branches whose original parent chain passes through the just-landed branch. This is an eager maintenance policy, not a GitHub requirement to push every remaining head before the next merge. [Execution order](https://github.com/danielbaars/anthracite/blob/a3c9f7055c7a42dfe38daee8fb843f21e1763474/apps/cli/src/actions/land_scoped.ts#L531-L609), [survivor selection](https://github.com/danielbaars/anthracite/blob/a3c9f7055c7a42dfe38daee8fb843f21e1763474/apps/cli/src/lib/landing_progress.ts#L301-L317).

Maintenance first reparents direct surviving roots and replays every affected unfixed branch. It then records existing PR associations and visits every survivor for publication. A changed published head is pushed with its captured lease and read back; an unpublished survivor remains unpublished. Consequently a branch higher in a chain can be rewritten and pushed again after each lower merge. An already matching remote head is not pushed. [Replay](https://github.com/danielbaars/anthracite/blob/a3c9f7055c7a42dfe38daee8fb843f21e1763474/apps/cli/src/actions/land_maintenance.ts#L74-L179), [publication](https://github.com/danielbaars/anthracite/blob/a3c9f7055c7a42dfe38daee8fb843f21e1763474/apps/cli/src/actions/land_maintenance.ts#L205-L283).

For a pure chain of n selected PRs **when each merge changes every future local head**, this yields `(n−1)+(n−2)+…+1` feature-ref updates: potentially 21 for seven PRs. There are separately n landed-branch deletion pushes: seven more, or 28 client push commands in that seven-PR shape. Server-side GitHub merges are not client pushes; a test adapter may simulate them with its own pushes to trunk, which must be counted separately. Unchanged heads can lower the feature-update count, so the formula is conditional, not a universal runtime invariant. [Skip/no-op and leased push](https://github.com/danielbaars/anthracite/blob/a3c9f7055c7a42dfe38daee8fb843f21e1763474/apps/cli/src/actions/land_maintenance.ts#L223-L255), [deletion push](https://github.com/danielbaars/anthracite/blob/a3c9f7055c7a42dfe38daee8fb843f21e1763474/apps/cli/src/lib/git/land_cleanup.ts#L24-L42).

Both kinds of client pushes run the user's pre-push hook through the frozen-state guard. Reducing redundant feature publication can therefore reduce repeated local hook work as well as remote workflow triggers; landed-only deletion hooks remain. Batching ref updates in one push could reduce process/hook invocations, but would not by itself eliminate those ref updates. [Hook delegation](https://github.com/danielbaars/anthracite/blob/a3c9f7055c7a42dfe38daee8fb843f21e1763474/apps/cli/src/lib/git/frozen_push.ts#L9-L68).

## What must precede the next merge

The **next selected PR** must have its intended rewritten local head published, its existing PR based on trunk, and a verified remote head matching the saved lease/reached identity. Fresh policy, reviews, checks and trunk ancestry then gate the merge. Those effects cannot be deferred past that PR's own merge without changing the core safety contract. [Pre-merge guard](https://github.com/danielbaars/anthracite/blob/a3c9f7055c7a42dfe38daee8fb843f21e1763474/apps/cli/src/actions/land_scoped.ts#L773-L817).

The current helper also verifies or updates each surviving PR's base and dependency footer after requiring its GitHub head to equal its reached local head. It rereads the resulting identity and preserves title/draft state. Merely skipping a push while retaining this helper call will refuse; publication and PR reconciliation must be selected together. Deferred edits must still use fresh descriptions rather than cached text. [PR read/write/readback](https://github.com/danielbaars/anthracite/blob/a3c9f7055c7a42dfe38daee8fb843f21e1763474/apps/cli/src/actions/land_maintenance.ts#L285-L338).

## Candidate boundaries, not proven implementation

| Work                                                          | Deferral assessment                                                                                                                                                                            |
| ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Publication of a later merge target                           | Plausible until immediately before its own merge. Preserve its last verified published head/lease separately from its reached local head.                                                      |
| Publication of a surviving branch outside the merge set       | Plausible until final maintenance, if no earlier selected merge needs it. Publish existing branches only; local-only survivors must stay unpublished.                                          |
| Later PR footer/base updates                                  | Can be considered alongside its deferred publication, but this explicitly accepts temporarily stale remote presentation. Do not rely on unverified GitHub retargeting after a base is deleted. |
| Local direct-root reparenting before deleting a landed parent | Keep in an initial optimization: current local validation and leaf cleanup assume a coherent surviving graph.                                                                                  |
| Replay of every distant descendant                            | A larger separate change. It can postpone conflicts and repeated local work, but changes the meaning and ordering of mandatory maintenance and owned continuation.                             |

A published sibling directly under the bottom PR is affected at that parent's merge, not necessarily at every later merge. Conversely, a published survivor above the final merge target is affected through the entire selected chain. Evaluate per original ancestry, not “all branches in the repository.” The initial plan captures the whole affected descendant scope and leaves independent trunk stacks out. [Captured scope](https://github.com/danielbaars/anthracite/blob/a3c9f7055c7a42dfe38daee8fb843f21e1763474/apps/cli/src/actions/land.ts#L73-L91), [original-parent traversal](https://github.com/danielbaars/anthracite/blob/a3c9f7055c7a42dfe38daee8fb843f21e1763474/apps/cli/src/lib/landing_progress.ts#L301-L317).

## Recovery changes that cannot be skipped

The version-1 member record already separates reached local `head` from last verified `remoteHead`, and writes progress atomically with concurrent-record checks. However it does not declare “deliberately deferred until later” as distinct from “required publication interrupted.” Existing publication and saved preview rules must understand that distinction before deferral is a supported state. A partial landing must disclose outstanding local/publication/base/footer work, retain original leases, detect external changes, and finish all authorized survivors before clearing recovery. Legacy eager records need a deliberate compatibility decision rather than an implicit reinterpretation. [Record shape](https://github.com/danielbaars/anthracite/blob/a3c9f7055c7a42dfe38daee8fb843f21e1763474/apps/cli/src/lib/landing_progress.ts#L10-L89), [atomic persistence](https://github.com/danielbaars/anthracite/blob/a3c9f7055c7a42dfe38daee8fb843f21e1763474/apps/cli/src/lib/landing_progress.ts#L225-L272), [saved remote/local inspection](https://github.com/danielbaars/anthracite/blob/a3c9f7055c7a42dfe38daee8fb843f21e1763474/apps/cli/src/actions/land_scoped.ts#L423-L504).

Current replay recovery requires the exact pending suffix of affected survivors, owns the active rebase/continuation bytes, and validates participant refs/metadata, frozen state and worktree availability. `continue` finishes local replay only; explicit `land` resumes remote effects. Changing local replay to one-next-branch operation therefore affects more than a loop filter. Keeping eager local replay while deferring only remote publication is the smaller first candidate, although it still stops early on distant local conflicts and does not eliminate repeated local replays. [Saved suffix validation](https://github.com/danielbaars/anthracite/blob/a3c9f7055c7a42dfe38daee8fb843f21e1763474/apps/cli/src/lib/landing_progress.ts#L178-L206), [owned replay](https://github.com/danielbaars/anthracite/blob/a3c9f7055c7a42dfe38daee8fb843f21e1763474/apps/cli/src/actions/land_replay.ts#L27-L104), [local continuation](https://github.com/danielbaars/anthracite/blob/a3c9f7055c7a42dfe38daee8fb843f21e1763474/apps/cli/src/actions/continue.ts#L164-L179).

## Recommendation

First investigate **deferred remote publication with existing local replay**, preserving scope and all protection checks. For the bounded seven-PR chain, a target of six feature updates under the current replay/publish/verify-before-merge contract plus seven deletion pushes is a **design projection**, not measured performance of an implemented optimized CLI. Published survivors add necessary final publication; failures, interruptions, external changes and retries need their own acceptance. Do not promise an n−1 runtime guarantee, live GitHub compatibility or workflow-cost savings from source analysis alone. This is not a universal mathematical lower bound for GitHub rebase merging. The smallest initial scope can keep non-target survivor handling eager while deferring only future merge targets. A later specification should decide remote presentation, base deletion, pending-state disclosure and legacy recovery before implementation. See the [synthetic measurements](land-push-amplification-2026-11-09.md), including the existing final-trunk survivor-scope limitation.
